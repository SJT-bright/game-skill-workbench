# 激励广告复活的跨游戏状态契约

适用 Cocos 2.x/3.x、英化和重塑游戏中“看完视频继续当前一局”的入口。每款游戏填自己的状态观察器、画面锚点和动作探针。本页只规定不变量与验证方式，不预设生命、步数、牌、镜头节点名或复活次数。免费重开按新局规则单独处理。

## 先定义一次复活保存什么

在发起广告前记录当前关卡和本局标识，以及本玩法要保留的业务数据。业务数据可能是得分、棋盘、敌人、角色位置、剩余时间、已消耗道具或随机种子。再写清复活后允许改变的资源，例如生命值、步数、保护时间和复活机会。每项写出广告前、取消后、完整观看后、下一次操作后的预期。不要把页面名或 `playing` 阶段当成这些数据的替身。

给广告请求绑定本局标识与一次性请求标识。广告结果只作用于仍有效的那局与那次请求。完整观看最多兑现一次。取消、播放失败和超时不兑现。玩家已重开、返回首页、进入下一关，或新广告请求替代旧请求后，迟到的旧回调不得改写新局。需要持久化的奖励使用已有凭证或账本保证重试不重复发放，内存内效果在游戏重新加载后的行为按产品规则确定。

失败时保留可继续的世界对象或检查点。复活过程可经过“失败待选、广告进行中、奖励已确认、等待画面恢复、可玩”这些概念状态，项目可以使用自己的状态名。广告完成回调、应用 `onShow`、复活弹窗关闭、其他弹窗关闭可能按不同次序到达。只有当前请求的奖励确认、复活弹窗退出且本局所需的暂停原因全部释放后，才恢复输入。关闭弹窗的回调不应单独改变玩法阶段。实现中把“兑现资格”和“恢复世界与画面”做成可重复调用而结果一致的步骤，并用请求标识挡住迟到与重复调用。

复活最终应同时满足四组条件。

| 维度 | 通用不变量 | 观察方式 |
| --- | --- | --- |
| 业务 | 仍是原局，规则要求保留的数据还在，复活收益与资格正确，兑现一次 | 本局标识、业务快照、权益读数 |
| 运行 | 本局按规则解除暂停，物理、计时和输入恢复，其他原因造成的暂停仍受尊重 | 暂停原因、系统开关、下一次动作 |
| 画面 | 玩法主体、镜头、必要 HUD 与操作控件可见，失败弹窗及遮挡退出 | 实际截图、可见锚点、遮挡与屏幕位置 |
| 续玩 | 玩家能在恢复帧上认出目标，正常输入导致该动作特有的业务变化 | 输入前后读数、目标位置、下一帧 |

业务读数变化只能证明业务变化。引擎射线可能穿过纯背景命中被遮住的 3D 对象。节点 `active`、触摸成功、动画、计时自动变化和广告按钮消失也分别只能证明局部条件。四组条件要分别取证。

## 最小验收和按影响扩展

当前任务涉及复活时，至少从正常失败到达真实入口，做一次取消或播放失败，再做一次完整观看。取消后核对收益与资格，并确认入口能按产品规则再次使用。完整观看后先拍恢复帧并看图，再点击或拖动帧上可辨认的玩法目标，拍下一帧并核对这个动作特有的业务读数。确认同一局、所需画面和运行系统都恢复。再让本局进入下一次失败，核对资格和免费 Retry 的目标关卡与可玩状态。

只有当修改涉及广告回调、弹窗关闭、暂停管理、存档、重开、镜头或渲染层时，扩展到对应的顺序与交叉场景。例如广告完成先于弹窗关闭，弹窗先关而广告仍未完成，应用返回时仍有其他暂停原因，广告回调重复，或旧回调在新局到来。纯美术改动核对受影响画面并重跑复活画面与入口结果。只改其他独立广告位，不机械重跑全部复活场景。跨比例复核以受影响的布局和已有证据决定。

## 给共享检查器填写观察器

`ad_entries[].role` 明确写 `revive`。在 `ad_outcome.entries[入口ID]` 填写下列游戏特定观察器。它们是可执行的业务断言，避免常量 `true` 和仅查阶段名。

- `run_id_js` 返回稳定的当前局标识，必要时组合关卡与本局代次。复活前后相同，Retry 后应改变。
- `reward_js` 返回能辨认复活收益的读数，例如复活次数、生命或补充步数。不要只返回“画面已进入 playing”。检查器对比取消前后及完整观看前后。
- `cancel_js` 返回布尔值，核对取消后的页面、权益和资源。取消是否保留同一局由玩法规定，检查器另保存取消前后标识用于复盘。
- `after_js` 返回布尔值，同时核对本局玩法阶段、运行系统、镜头或背景遮挡、玩法主体、必要 HUD 和弹窗状态。能读取具体对象时检查实际对象，不用缓存的标志替代。
- `after_visible` 列出玩家完成下一步必须看见的节点。选择实际玩法主体与必要操作控件，按当前游戏结构填写。无可投影节点时用 `after_js` 的渲染条件和恢复帧人工看图补证。
- `revive_probe` 可填写本入口专用的 `probe` 与 `state_js`。否则使用 `resume_play` 的同名字段。`probe` 必须是实际点击或拖动，`state_js` 读数必须因这次动作而变化。自动计时、镜头动画、按下反馈不能充当动作结果。

共享 `ad_outcome` 对已声明的复活入口缺少这些字段、换局、画面锚点不可见或被遮挡、动作无业务效果和证据帧缺失会报失败。恢复帧和下一帧用于锚点与输入的技术核对。复活后画面是否闪黑、缺图或被遮住，随人工试玩观察。当前项目可沿用既有 adapter 与运行器，无须另造一份平行测试框架。

## 回归用例如何设计

用一个真实成功案例和一个已知失败案例校准观察器。已知失败可以是缺 HUD、玩法主体被背景遮住、复活后换局、输入仍暂停或旧回调发到新局。先证实观察器能拦住失败，再证实正常复活可通过。保存广告前状态、取消返回帧、完整观看后的恢复帧、输入后的帧和相应业务读数。若源码只改了局部复活流程，按受影响状态局部验证。已有证据只在同一构建、同一观察器与同一判定口径下复用。

测试报告明确写出模拟广告、本机浏览器或真实平台回流各自的证据来源。真实平台回流仍按当前项目的广告验收要求执行。
