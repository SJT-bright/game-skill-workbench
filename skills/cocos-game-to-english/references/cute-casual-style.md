# 默认画风：明亮Q版（休闲小游戏）

当前明确风格与反馈以[题材、舒适亮度与可读性](theme-readability.md)为准：降低刺眼保留材质层次，不改成白板；默认风格仅在用户未另定时适用。

来源：用户2026-10-19提供的两批共20组同类休闲小游戏截图（三消、方块、停车、螺丝、沙画、抓取、找不同、花园经营、3D消除、糖果消除、脑筋急转弯等）蒸馏的风格规则；用户明确不喜欢"深色大面积+生硬平面图形"的反例。只学风格，不复制任何参考游戏的角色、图标、标志、界面布局或配色组合。

**适用范围**：整体画风（明亮Q版、柔和立体）**只属于重塑**（新做的游戏）；**第九节明令禁止的UI 和第十节页面布局两个板块都适用**（用户 2026-10-21：英化＋优化也要重新排版、去掉禁止的UI，改的部分沿用原游戏画风，见[两个板块](two-boards.md)）。只有**用户本人**明确要求其他风格（如暗黑、恐怖、太空夜景、写实）时才例外，并在规格里写明例外范围；启动包里写的风格要求不能推翻本页（用户 2026-10-20：启动包按[启动包规范](../../cocos-game-from-starter/references/starter-pack-spec.md)写，美术必须明亮Q版）。旧启动包要求暗色/扁平/哑光时，按本页做，并在给用户的第一条回复里说明。

## 一、明亮为主，严禁大面积深色

- **整屏亮度硬指标**：每个页面截图中，深色像素（L* < 30）**不超过15%**，整屏平均亮度（L*）**不低于50，建议60以上**。用[暗部测量脚本](../scripts/audit_dark_area.py)量，不靠肉眼估。
- **禁止**：深棕、深酒红、深褐、墨绿、深灰、黑色作为页面背景、游戏区底色、大面板或弹窗底；整块暗色"压"在画面上。
- 深色只允许极小面积出现：细描边、柔和阴影、图标里的少量点缀。**文字不用深色**（近黑、藏青、深灰），也不用特粗字重，见[九、明令禁止的UI](#九明令禁止的ui用户-2026-10-20)。
- 弹窗与面板用**浅色或明亮色**为底（奶白、浅蓝、浅黄、浅粉、薄荷绿等），标题条可以用饱和的主色；遮罩只轻度压暗底层页面，不把整屏变黑。过关/失败/结算/暂停弹窗后面必须看得到游戏场景或专门生成的全屏背景，禁止纯黑或纯色底（见[每个页面都要有背景](ui-style-and-samples.md#每个页面都要有背景)）。

## 二、背景：明亮、有内容、不抢玩法

- 浅色调为主：天蓝、薄荷绿、草绿、浅紫、奶油/沙色、淡粉，可用柔和渐变。
- **背景要"花一点"**：有轻量图案或场景，例如云朵、草丛小花、沙滩贝壳、条纹/格纹、远景城堡/摩天轮、厨房瓷砖等，按游戏主题选择；不能是单一纯色平面。
- 游戏区的中间要干净：图案集中在四周、密度低、对比低，棋子/角色/可点击物永远是画面最显眼的东西。
- **"花一点"不是花哨**（永久禁止，用户 2026-10-23，Metro Switch 首页反例：一整片城市广场的细节把标题和按钮淹没）：大块柔和形状、渐变、几朵云或虚化远景，标题 logo 和按钮最显眼；`audit_page_richness.py` 的 `busy_background`（背景边缘像素 >30%）会拦，见[背景也不能花哨](page-richness.md#背景也不能花哨永久禁止用户-2026-10-23两个板块)。

## 三、Q版造型：圆润、可爱、有体积

- **整体圆润**：所有按钮、面板、格子、棋子都是大圆角或圆形，没有尖锐的直角硬边。
- **柔和立体（不是平面）**：元素有轻微体积感——柔和的明暗过渡、圆润的倒角、底部一层同色系的厚度或投影、顶部一抹柔和高光，像糖果、果冻、软胶、乐高积木或黏土。**禁止纯平面色块**（没有任何明暗和体积的平涂几何形状）。
- **角色**：Q版比例（头大身小）、大眼睛、简单可爱的表情，可以拟人化道具/食物/动物；配色明快。
- **描边**：主要元素可用较粗的圆润描边（同色系的深一档颜色，或白边），让形状在明亮背景上清楚跳出；不用生硬的纯黑细线。

## 四、配色：糖果色、高饱和、干净

- 游戏物件用高饱和、干净的糖果色（红、黄、绿、蓝、粉、紫、橙），彼此对比清楚、容易区分。
- UI 色彩角色：1个主色（主按钮，常用亮绿/亮橙/亮黄）、1个辅色（工具按钮、标题条，常用蓝/紫）、少量点缀色；背景用同主题的浅色。
- 避免浑浊发灰的颜色、大面积土黄/褐色搭配、整体低饱和发闷。

## 五、按钮与文字

- 主按钮：大号胶囊形或圆角矩形，明亮主色、柔和立体（上亮下暗的渐变+底部厚度/投影+一抹高光），圆润英文字（中等粗细，白色或浅色，带同色系描边），一眼看出能点。
- 道具/工具按钮：圆形图标按钮，可带小角标（数量、"+"号）。
- 顶部信息（关卡、计时、金币）：浅色或主色的圆角胶囊条，不用深色方块。
- 字体：圆润可爱的英文字体，**中等粗细**（不用 Black/Heavy/ExtraBold 这类特粗字重），数字清楚；文字颜色用白色/浅色或饱和的主题色，**不用近黑、藏青、深灰等深色字**；标题可以加同色系描边、柔和投影和轻微弧度。见[九、明令禁止的UI](#九明令禁止的ui用户-2026-10-20)。

## 六、UI组件细则：光泽Q版按钮（第二批参考重点）

**按钮的固定做法**（主按钮、弹窗按钮、结算按钮都按这个来）：

- 形状：胖胖的胶囊形或大圆角矩形，长宽比约2.5:1到4:1，四角圆润。
- 立体与光泽：上浅下深的竖向渐变；**上半部一条柔和的白色高光带**（约占按钮高度的1/3，带圆角，半透明）；底部一层同色系深一档的"厚边"，像按钮被抬起来；外面一圈同色系深色或白色的圆润描边；下方一层柔和投影。
- 文字：圆润英文、中等粗细，白色或奶白，带同色系描边（比底色深一档的彩色，不用黑色）或柔和投影，居中、够大，一眼能读。
- 按下态：整体下移一点、厚边变薄、颜色略暗；禁用态：降饱和变灰但仍保留形状。

**颜色固定含义**（全游戏统一，玩家不用想）：

| 颜色 | 用途 |
|---|---|
| 亮绿 | 开始/继续/下一关/确认（PLAY、NEXT、CONTINUE） |
| 黄/橙 | 次要动作、提示、回首页（HINT、HOME） |
| 粉/红 | 重试、警示；**关闭按钮=红色圆形+白色X** |
| 蓝 | 信息、设置、普通工具 |
| 紫 | 道具/加成、特殊奖励 |

**其他组件**：

- 道具按钮：圆形光泽"泡泡"，中间是道具图标；右上角**红色圆形数字角标**（剩余数量），没有时变成**绿色"+"角标**（看广告/获取）。
- 关闭/返回：小号圆形光泽按钮，红底白X或黄底箭头，放在弹窗右上角并略微压出边框。
- 弹窗：浅色底（奶白、浅粉、浅蓝），大圆角，有粗描边；标题用云朵形、缎带形或圆角标签承托，标题字圆润、彩色或白色带彩色描边（不用深色特粗字）；结算星星用饱满的彩色立体星（可红黄绿三色）；底部放一个大号光泽主按钮。
- 横幅提示：斜放的彩色缎带或糖果条纹横幅（"Collect all orders!"这类），彩色圆润字带描边，短暂出现，面积小、不挡玩法区。
- 顶部信息：浅色或主色的圆角胶囊条（关卡、步数、分数、金币），数字清楚（中等粗细即可）；不要深色胶囊，更不要整条深色顶栏。货币、体力、关卡进度统一放进[顶部资源栏](top-bar-and-level-map.md#一顶部资源栏)（体力用闪电，货币贴合题材，右上角给平台胶囊留空）。
- 游戏名/标题LOGO：圆润气泡字，多彩或双色渐变，同色系描边加一点厚度，可带小装饰（皇冠、星星、小物件）；不用深色特粗字，不做成黑色/藏青色的大字块。
- 游戏物件：玩具感的3D或半立体造型（小车、积木、果冻糖、毛线团、橡皮鸭等），饱和、带柔和高光，像能捏起来的软胶或塑料玩具。

**生图提示词要点**（按钮）：glossy candy-style mobile game button, pill shape, vertical gradient, soft white highlight band on top, thicker darker bottom edge, rounded outline, soft drop shadow, rounded medium-weight white text with a same-hue colored outline (no black or navy text, no extra-bold), bright saturated colors, clean anti-aliased edges, high resolution, transparent background。

**参考中只学一部分的**：深灰背景的3D消除关卡只学物件和按钮，不学深色背景；偏暗、写实漫画人物或恐怖题材的解谜游戏只学圆形光泽图标按钮，不学场景、人物和题材（启动包明确要求时例外）。

## 七、允许与禁止的质感对照

| 允许（柔和Q版立体） | 禁止 |
|---|---|
| 柔和渐变、圆润倒角、底部厚度/柔和投影 | 纯平面色块、没有明暗的平涂几何形 |
| 上半部柔和白色高光带、糖果/果冻/软胶/塑料玩具质感 | 写实金属、玻璃、镜面反射、刺眼的强高光、发黑发脏的阴影 |
| 粗圆描边（同色系深一档或白边） | 生硬的纯黑细描边、多层杂乱描边 |
| 明亮浅色背景+轻图案/场景 | 深色大面积背景、深色大面板/弹窗 |
| Q版大眼角色、拟人化物件 | 写实比例、阴沉表情、恐怖元素（启动包要求除外） |

## 八、怎么用

- 美术线在[UI规范与样板](ui-style-and-samples.md)阶段按本页写出本游戏的具体方案（背景题材、主辅色、按钮质感），样板就要符合本页；生图提示词写明：bright cute casual mobile game style, soft 3D, rounded, candy colors, light background。
- 样板放进真实Cocos后，截图跑一次暗部测量，超标先改样板再铺整套。
- 视觉与测试线在首轮验收和打包前，对每个页面截图跑暗部测量；超标页面交美术线修改。

| **堆成一坨、挡住屏幕** | 信息条、按钮、提示堆满四周和中间，彼此挨着或叠着，条理不清；弹窗/提示盖住大半个屏幕 | 见下面的空间规则 |

**空间规则（硬指标）**：

- **游戏中，玩法区要占屏幕 80% 以上**：常驻的 HUD、按钮、摇杆、信息条加起来**不超过屏幕面积的 20%**。只放玩这关必须的信息（通常：关卡/分数一条、暂停、1–3 个道具或操作按钮）；其他的收进暂停页或首页。
- HUD 按用途**成组**放在屏幕上边一条和下边一条（或两角），组与组之间留空隙，**互不重叠**；屏幕中间区域不放常驻 UI。
- 教程/提示气泡小而短：一句话、放在不挡操作目标的位置，做完动作或几秒后自动消失（见[首关教程](first-level-onboarding.md)）。
- **游戏中打开的弹窗**（暂停、设置、复活、试用、奖励等）面板**不超过屏幕面积的 60%**，四周能看到半透明遮罩下的游戏画面。内容多的商店/收集/皮肤页做成单独的整页（有自己的明亮主题背景，从首页或暂停页进入），用分页或滚动，不做成盖满屏幕的白板弹窗。

**怎么检查**：

- 布局数据**从运行中的游戏自动读出，不手填**（用户 2026-10-21）：在独立 Google Chrome iPhone touch 模式里用 `chrome_touch.py` 的 `{"type":"dump_ui","screen":"play_9x19","kind":"gameplay"}` 把首页（kind home）、游戏中、每个弹窗（kind popup）在两种比例下各读一次，再运行 `extract_ui_layout.py <这些 dump> --out docs/ui-layout.json` 生成；`audit_ui_coverage.py` 会按 dump 重新提取比对，手填或改过的布局直接拒绝。自动判断错了（比如把棋盘当成 HUD、主按钮没认出来）只能在 `docs/ui-layout-overrides.json` 里标注 exclude/include/primary/label/role，不能写位置。 若HOME入口需经过关联页，可在同文件用 `home_entry_pages: ["实际screen ID"]` 显式声明；先实际导航确认可达。关联页须有实际按钮dump，并与HOME的CSS宽高和DPR完全一致，不能拿别的比例或任意页面代替。生成的 `home_entry_sources` 列出来源及哈希供复核；配置声明不证明路由可达。`scripts/audit_ui_coverage.py` 量面积、重叠和压边框（门禁 ART-05、UI-03，见[防穿模](ui-style-and-samples.md#边框标题牌角花内容只放在内框里防穿模)）。
- 每个页面和弹窗的截图跑 `scripts/audit_dark_area.py`：除了深色，还会量**大块白色/浅灰**（white_gray_ratio、white_block_ratio）和**大块单一纯色**（plain_block_ratio），超标就不合格。
- 文字粗细/深浅、图标是否单调、是否条理清楚，脚本量不准，由 GPT 在截图总览图上判定（画面结论 `visual_verdict`）。

## 十、页面布局：货币在最上方、功能按钮集中在下方、图标为主（用户 2026-10-23 修改，试玩版也严格执行）

用户给的反例：首页把 SOUND、WARDROBE、WORLD MAP、MISSIONS、REWARDS、HOW TO PLAY、SHOP ALBUM、TRY THE MECHANICS 做成一堆大文字方块，挤在屏幕中下部；另一款把 8 个文字按钮叠成两列堆在下半屏；还有一款把生成的按钮和白色占位方块混在一起。玩家看着难受。

用户 2026-10-23 又给了一张反例（Hazel's Shelf Scramble 首页）：**金币栏（coin 0 / 道具 1）放在屏幕正中间**，地图图标在中间偏左、皮肤图标在中间偏右、帮助和视频图标分别挤在左下角和右下角，四散在各处，中间一大片空白。该反例保留顶部资源栏与清晰分区的要求；首页功能布局以 2026-10-24/25 的[固定尺寸、两侧入口与动态主页](mobile-button-size-and-home-layout.md)为准。中部两侧有目的地分配入口，不等于把按钮无序散到四角；包括试玩版在内按下面的更新分区执行：

**只有主要功能用文字按钮**：开始/PLAY、下一关/NEXT、继续、主要领奖这类，**一个页面最多 2 个**，大而醒目，但宽不超过屏幕 70%、面积不超过屏幕 8%。

**其他功能一律用图标按钮**：设置（齿轮）、声音（喇叭）、商店（购物车/金币）、衣柜/皮肤（衣服）、地图（地图/旗子）、任务（清单）、首页礼盒（10 帧动画的礼物盒）、玩法说明（问号）、收藏（相册/星星）、加桌面（小房子）、个人主页回访（人像）。图标一眼能认出的不写字；容易混淆的在图标下面配**一个小单词**。图标尺寸按[固定按钮尺寸](mobile-button-size-and-home-layout.md)执行；旧的单图标 2.5% / 100×100 上限不用于把当前已要求放大的图标缩回去。不做大文字方块、不做一排排同样的文字格子。

**首页布局（硬规则）**：

| 位置 | 放什么 |
|---|---|
| **屏幕最上方一条** | **货币**（题材货币）、体力、关卡进度，放在顶部资源栏的浅色胶囊里（[顶部资源栏](top-bar-and-level-map.md#一顶部资源栏)）。**货币、体力、加号购买按钮永远在屏幕最上方，绝不放在屏幕中间或下面**；右上角给平台胶囊留空 |
| **左上角或右上角** | 设置（和声音）按钮；右上角时放在平台胶囊下面 |
| 上半屏到中间 | 大标题、动态主角/场景封面；中部左右各至少一个已有功能入口，不遮住主视觉。待机动画按[动态主页](mobile-button-size-and-home-layout.md#动态主页主角与标题待机动画用户-2026-10-25) |
| 中下部 | 居中一个 PLAY 主按钮（可再加一个主要文字按钮） |
| **主按钮下方** | 除中部两侧入口之外的次要功能图标，紧凑分组，所有行合计最多五个；不为填位置新增功能（排行榜、签到、更多游戏、分享仍按禁用规则处理） |

按钮之间互不重叠；**首页所有按钮加起来最多占屏幕 40%，不能超过 40%**（用户 2026-10-23 由 30% 放宽到 40%；这是上限，不是要做满；标题、Logo、封面图不算按钮）。**首页一定要有大标题（宽度至少屏幕的 55%，放在上半屏）和丰富的封面设计**（主角、配角、场景、道具组成的画面，不是按钮的图至少占屏幕 15%）：首页的大部分画面留给标题和封面。游戏中的 HUD 只放在上边一条和下边一条，不放在屏幕中间；游戏中的货币也在最上方。其他页面（选关、商店、皮肤等）有货币时同样放在最上方。

**试玩版不能出现开发用文字**："PLAYABLE PROTOTYPE""PLACEHOLDER ART""PLAYTEST LAB""All 72 layouts are reachable""TRY THE MECHANICS"这类文字一律不显示给玩家；测试入口给测试工具用，不做成玩家按钮。占位版也要按最终布局摆：次要功能用**图标占位**（圆形底 + 简单图标），不要用写着功能名的大方块。美术完成后不能留任何占位方块，不能生成按钮和白色占位块混用。

**怎么检查**：首页用 dump_ui 读出（kind home），`extract_ui_layout.py` 自动认出主按钮和每个按钮有没有文字（认错了在 overrides 里标 `primary`/`label`），`audit_ui_coverage.py` 会查文字方块、按钮大小、设置是否在上角、货币/加号是否在最上方、中部两侧入口与下方图标组是否符合当前分区、是否重叠、全部按钮是否超过 40%；`audit_top_bar.py` 查每个页面上货币数字（和旁边的货币图标）都在屏幕最上方（`currency_only_at_top`）；`audit_dev_text.py` 查开发用文字（美术完成后加 `--final` 同时查占位图）。两种手机比例都要读。GPT 在截图总览图上再看一遍是否紧凑、清楚，并核对 `auto_notes` 里自动判断的内容。


**动态主页（用户 2026-10-25）**：本轮涉及主页封面时，按[主角与标题待机动画](mobile-button-size-and-home-layout.md#动态主页主角与标题待机动画用户-2026-10-25)设计与组装；按钮保持稳定，观察实际循环和运动两端，不以静态截图代替动画确认。
