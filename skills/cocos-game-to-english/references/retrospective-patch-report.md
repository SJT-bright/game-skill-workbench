# 交付后复盘补丁报告

每款游戏成功交付、[经验回流](../../remake-core/references/production-learning.md)的收集完成之后，制作本作的 AI 自己做一次复盘，产出一份给人看的《复盘补丁报告》和一个可以直接交给英化 Skill 会话的补丁文件夹。

这份报告回答三件事：这次哪里做得好、哪里做得不好；每条经验的证据和根因是什么；它下次应该放进 Skill 的哪个文件、哪个制作阶段。经验必须是已经对照过整个 Skill 分析好的，不能只是一句“下次注意”。

报告不决定游戏能否交付，不运行游戏、浏览器或任何检查，不修改、不安装、不发布 Skill。用户批准之前，已装 Skill 一个字节都不变。

## 什么时候做

- 游戏已交付，用户没有在等别的事。交付回复先发，复盘随后做，不让用户等。
- 同一款游戏交付后的返工再次交付时，重新取事实并更新报告，旧报告保留。
- 游戏还在制作中途不做；Skill 维护会话不做。

## 三步

`T` 是 `<本 Skill>/scripts/retrospective_report.py`，`P` 是游戏工程。

```sh
python3 -B "$T" facts  --project "$P"
python3 -B "$T" check  --project "$P"
python3 -B "$T" render --project "$P"
```

1. **取事实**。`facts` 只读本作已有的 `docs/timing/timing-summary.json`、`docs/test/package-issues.jsonl` 和经验包，写出 `docs/production-learning/retrospective/facts.json`。同时按[额度记录](#各阶段的额度记录)读出每个阶段消耗的模型用量。它会自动挑出五类异常信号：某阶段用时占全程四成以上、某阶段用量占全程四成以上、某阶段有超过 30 分钟没有节点记录、单个节点超过 60 分钟、同一节点在同一阶段执行三次以上。信号是必须回答的问题，不是结论。
2. **写复盘**。AI 按下一节的要求写 `lessons.json`，把改好的 Skill 文件放进 `patch/改动文件/`（按 Skill 包内相对路径）。然后 `check`，有缺项就按提示补，直到通过。`check` 返回 2 只表示复盘没写完整。
3. **出报告**。`render` 写出 `复盘补丁报告.html`，以及 `patch/` 里的改动清单、底本校验、逐行差异和一段发给英化 Skill 会话的话。最后在聊天里用两三句话告诉用户：几条经验、几条建议改 Skill、报告在哪。

## 各阶段的额度记录

时间之外，每个阶段消耗了多少额度也要记。数据来自 Codex 自己留在本机的会话记录（`~/.codex/sessions`），工具只读，不需要制作过程中额外做任何事。

```sh
python3 -B "$T" usage --project "$P"
```

它按阶段计时里每个阶段的起止时间，把本作的会话记录切开，每个阶段给出：模型调用次数、总用量、其中非缓存的用量（新输入加输出，更接近真实消耗）、周额度百分比涨了多少、占全程比例，并写入 `docs/timing/usage-summary.json`。`facts` 会自动带上同一份数据，报告里单独一张表。

- **算谁的**：工作目录是本作的会话，加上由它们派出的子代理和审批复核会话。别的游戏的会话不算。
- **用量是准确值，周额度百分比只作参考**。百分比是整个账号的，同一时段有其他会话在跑时会一并上涨，表里会标出“同时段另有几个会话”；百分比是整数，很短的阶段可能显示 +0%，这时看用量。额度周期在阶段中途重置时不相减。
- **没有就写没有**。不是 Codex 制作、换过电脑、或会话记录已清理时，显示“无额度记录”，不估算、不倒填。所以要在交付时就跑，把结果存进游戏工程。
- 每个阶段结束汇报用时的同时，可以跑一次 `usage` 一并报出这个阶段的用量；这只是读记录，不算一次检查。

复盘时把时间和额度放在一起看：时间长、用量也高，多半是反复构建采集或反复读大文件；时间长、用量低，多半是在等构建或等用户；时间短、用量高，多半是一次读入了过多无关内容。结论要落到具体节点上。

## 复盘怎么写

先读事实，再读 Skill，最后才下结论。顺序不能反。

**自我复盘**（`reflection`）：做得好的、做得不好的各至少一条，每条一句完整的话，带具体数字或节点名；再写一句话总评。不写客套话，不把等待用户的时间算成自己慢，也不把自己的返工说成新增工作，归类按[重复检查收敛](repeat-check-convergence.md#三新增工作与返工分开记)。

**每条经验**（`lessons[]`）必须写全：

| 字段 | 要求 |
|---|---|
| `what_happened` | 发生了什么，一两句 |
| `evidence` | 至少一条，写明出处和具体数字或原文。没有证据的只能算猜测，不写进来 |
| `root_cause` | 根因，不是现象。“检查失败了三次”是现象，“第二阶段没有先做首件”才是根因 |
| `kind` | `process` 流程、`tool` 工具、`rule_gap` 规则缺口、`project_only` 本作特有 |
| `signal_ids` | 这条经验回答了哪些异常信号 |
| `skill_analysis.read_files` | 为这条经验实际读过的 Skill 文件。必须真的打开读过，工具会核对文件存在 |
| `skill_analysis.existing_rule` | Skill 现在是怎么规定的 |
| `skill_analysis.why_not_prevented` | 现有规定为什么没拦住 |
| `skill_analysis.conflicts` | 和现有规则是否冲突、重复，或者已经有了只是没执行 |
| `prevention` | 下次在第几阶段、用什么制作动作预防 |
| `patch.decision` | `change_skill` 改 Skill、`project_only` 只留在本作、`no_change` 不改；都要写 `reason` |
| `patch.adds_check` | 是否增加检查，必须明确写 true 或 false |
| `patch.changes` | 要改的每个文件：包内相对路径、当前文件的 `before_sha256`（新文件为 null）、一句话说明 |

所有异常信号都要有去处：被某条经验回答，或者在 `unanswered_signals` 里写明为什么不需要回答。

## 对照整个 Skill 分析时要做到的

1. **先找现有规则**。在 Skill 里搜这个问题相关的阶段、节点和关键词，读到具体段落。现有规则已经覆盖、只是这次没执行的，结论是“没执行”，经验写清楚为什么没执行，不再加一条重复的规则。
2. **落到最早能预防的制作阶段**。能在第 1、2 阶段的盘点、规划、接线里消除的，就不放到第 3、5 阶段去查。
3. **改最少的地方**。优先在已有页面的对应小节加一两句；确实没有合适位置才新增页面，并在入口加一句指向。同一条规则只写在一处，别处用链接。
4. **不靠多加检查吸收经验**。`adds_check` 为 true 时必须说明为什么制作阶段预防不了。四条已永久撤销的做法（完整美术回执、默认录屏、改一点就全量重测、另一条写包路线）不能以任何名字带回来。
5. **不动工具身份里的文件**，除非这条经验本身就是工具缺陷并且手里有能复现的反例。改工具脚本会让已有游戏的记录需要重新实测；这种情况写 `project_only`，在 `reason` 里说明缺什么，等拿到反例再单独出补丁。
6. **本作特有的不外推**。游戏名、关卡、金额、某个专用键只留在本作，`decision` 写 `project_only`。
7. **补丁必须基于当前已装的 Skill**。`before_sha256` 取自已装文件；别的补丁先改过同一个文件时，以最新的已装文件为底本重做。

## 交给谁

报告和补丁留在游戏工程的 `docs/production-learning/retrospective/`。用户看过报告后：

- 同意：把 `patch/发给英化skill_复盘补丁_复制这段话.txt` 的内容发给英化 Skill 会话，由它合入、发版、安装。游戏会话自己不安装。
- 不同意某条：用户说编号，把那一条的 `decision` 改成 `no_change` 并写明原因，移走对应文件，重新 `render`。

多款游戏的补丁由英化 Skill 会话攒批合并，在没有游戏正在制作时安装，见[重复检查收敛](repeat-check-convergence.md#二第-3-阶段的循环上限)第 4 条。
