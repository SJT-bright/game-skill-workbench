# 审查执行顺序与去重

**美术检查前移（用户 2026-10-25）**：按[美术验收前移与试玩后锁定](art-before-trial.md)执行：所有美术测试在交用户试玩前完成；用户确认后到测试包交付之间不再美工测试、不重新评判已批准画面。最终画面字段只查运行故障，不夹带美术标准。


修订：`2026-10-26.contracts-v3`。用于压缩重复执行，不削弱正式 writer、真实证据或当前项目的必要检查。先按[任务范围](testing-scope-and-stop.md)选日常、核心逻辑或完整验收，再执行本页相应阶段；与旧文的重复执行、逐关套全流程、每次包前重新玩整份清单冲突时，以本页为准。

## 玩法确认前的短检查

首个玩法候选交用户前，先验证真实启动、可信输入、基础胜败/结算、免费重开和最小奖励存档；数据/资源明显错误先修。完整广告/存档/加载故障矩阵放在玩法确认后的稳定候选一次执行。当前已报告启动或奖励故障仍先定点闭合，不能借阶段顺序跳过。用户只要试玩时不自动全量验收或出包。

## 一、全流程只有一次完整执行，后续核证据和变化

| 阶段 | 做什么 | 不重复做什么 |
|---|---|---|
| 1 范围与输入 | 确认游戏、候选、改动和已有验收；列实际适用功能及关卡必测清单 | 不重读所有事故报告，不把别的游戏固定测试数量搬进来 |
| 2 设计与数据 | 首次制作核关卡配置、资源引用、数值与模块；有解法/模拟器时检查所有关卡可解性，并注明方法边界 | 自动遍历全部配置/解法不等于要求人工逐关游玩；未改设计不重开设计关 |
| 3 美术与适配 | 美术阶段核真实页面/条件状态、字与底图、遮挡和两种比例；修后复查受影响页面 | 最终功能检查不重新做美术审美、全部素材放大和两轮美术自查 |
| 4 一次功能与关卡执行 | 在当前候选采集正常流程、关卡抽测、按钮、加载/奖励/存档故障及动态画面 | 相同一次操作、录屏、dump 可对应多个检查 ID，保留各自观察；不因表格不同再操作一遍 |
| 5 修复与增量回归 | 修改缺陷后重测受影响关卡、状态、共享依赖及相关旧问题；版本绑定按工具实际支持处理 | 不因改一个按钮/一关就重开前15关和整个基础抽测，不刷旧报告哈希冒充新执行 |
| 6 最终核验 | 读有效报告、原始失败及已关闭证据、版本与最终画面；补失效项和实际疑点 | 同一个 Codex 已亲自执行且未改，不再固定另走至少3流程；不同执行者按下面独立复核条件执行 |
| 7 已授权出包 | 正式 writer 核当前自动门禁、Native 路径、存档/覆盖、体积、ZIP 回解与字节 | 不在门禁已经接入后再手工重复所有相同脚本；不把ZIP改名当成新一轮人工验收触发 |

设计/美术首次完整验收标准继续有效；用户试玩确认沿用已授权节点，不为本页再加审批。只要求试玩或局部审查的任务到对应结果即交付，不自动出包。

## 二、关卡抽测与共用功能分开安排

- **完整基线沿用原抽测密度**：1–15 每关；16–30 间隔1关；31–40 间隔2关；41–50 间隔3关，随后每10关再增加间隔。加末关、所有新玩法首现关、本轮修改关和与本轮相关的历史故障关，去重后执行。
- 不含额外首现/修改/故障关时，70关选35关、100关选40关、200关选51关。这是待执行清单，不是通过数量。若首现标记等导致全部关都入选，检查真实原因；不可为了省时删除实际新玩法。
- **每个抽中关卡查该关的玩法**：真实操作、关卡目标/胜负规则、正常完成和结算/进度。只需与该关机制有关的失败或特殊分支；同一个共用 Retry、Home、广告故障矩阵、坏存档矩阵不在每关重复。
- **共用功能按实际入口与机制覆盖**：每个真实广告/领取入口的奖励、取消和状态仍要验证；加载与存档机制矩阵不能省。相同生产路径在同构关卡重复出现，不扩成“关卡数 × 全部故障 × 全部视口”。关卡有不同奖励逻辑、boss、限定/奖励关、独立资源分包或特殊状态时，另选代表并给原因。
- **第二种比例看适配与输入风险**：两种比例的页面、关键触摸、重开及当前门禁规定的双比例加载证据仍保留；不无条件再通关整份关卡清单。故障矩阵只有视口会影响机制、实际失败、或现有门禁明确要求时才双比例重做。
- QA 跳关仅用于到达待测关，到了仍真实操作；QA 标记不可进入上传包。只查配置、解算器通过或直接调用回调均不能写成真实游玩。

完整基线：

```sh
python scripts/plan_level_tests.py --level-plan <实际关卡表> --out <新清单.json>
```

局部修复已有完整基线时，按真实差异及依赖列关号；例如以下数字只是参数格式：

```sh
python scripts/plan_level_tests.py --level-plan <实际关卡表> --scope changed \
  --changed-levels 18,25-26 --related-levels 27 --regression-levels 69 \
  --out <新局部清单.json>
```

`changed` 只选声明的改动/关联/历史故障关，并补这些关所用机制的首现关；不自动加入无关的前15关、末关或所有首现关。新增清单的 `selection_reasons` 逐关说明入选原因。完整出包是否须重新跑完整清单，由实际改动和现有门禁的证据有效性决定；此参数不接受通过状态，也不修改 writer。

## 三、加载、录屏和最终验收怎样去重

- 第一次功能轮尽量在已完成组装的候选上做；后面只是写报告且字节未变，最后一段核加载报告即可，不固定把第一次加载矩阵再执行一次。
- 加载链、资源/分包、引擎/适配器或其证据绑定变了，就在最终产物重跑失效矩阵；工具采用全树绑定且不支持依赖级复用时，按它要求真实重跑。不伪造局部复用。
- 关卡/按钮操作时同步录动态画面、dump 和关键日志；相同状态同一轮有效证据可分别支持按钮、英文、视觉与状态检查，不另开同样一轮采集。不同断言写各自实际观察，不能复制同一句“正常”。
- 同一个 Codex 自己执行测试并最终核验时，不触发独立执行者复核；`check_known_issues.py` 当前仅在 `test_executor` 不是 gpt/codex 时要求 `gpt_spot_check`。不能改 executor 身份省检查。
- **其他 AI 执行时保留现有硬约束**：Codex 读全部改动、亲自重跑全部适用自动脚本并抽查至少3个流程，发现不符重测该类。现脚本要求 `rerun_auto_checks:true`，本次未放宽；文档不能将其解释成只读旧报告即可通过。

## 四、停止条件与成本边界

执行前先拦住会使长测失真的条件：实际候选/运行身份不符、测试页操作互扰、必要资源缺失。确认后先修该阻断，不在错误版本上继续刷关、赚测试资源或跑长矩阵；其他独立且有效的工作继续推进。

同一范围内优先执行便宜且能直接判断的项：现有数据/依赖/体积检查、首条异常与一次关键真实操作，再进入适用的昂贵故障或关卡流程；没有对应改动或具体信号不增加后者。不要为“省时”另建与现有检查器重复的快检工具。

完整日志/报告落项目，先读结果摘要、首错和本轮差量；批准检查结论前仍核对应原始证据，遇失败、覆盖缺口或摘要不一致时定点回溯原始记录，不让摘要替代证据。一次操作的证据可支持多个真实断言；可复用的判断按当前工具支持的候选、依赖和检查器版本核效，不重复开页面、全量dump或重读长事故历史。沿用现有报告记实际耗时与扩测原因，不为成本统计新建一套清单，也不承诺未经测量的节省比例。

已完成本轮适用检查、缺陷已关闭、证据与版本有效且无新疑点，就收尾并交付。报告沿用一份进度和门禁表，最终总结引用同一行结果，不再另抄一份18行观察报告。保留原始证据和适用性，不合并删除真实断言。

现有全树绑定、STORAGE/LOAD的实际runner重放、writer拒绝对照及特定项目维护协议仍可能耗时。这些是尚未实施缓存/依赖绑定的工具边界；不能只靠这页文字减少实际必跑项。进一步改这类工具须另以具体耗时证据和正反用例验证，不承诺本次节省固定比例或保证零错误。
