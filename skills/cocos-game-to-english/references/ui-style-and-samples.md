# 每款游戏的 UI 美术规范与样板

当前明确风格与反馈以[题材、舒适亮度与可读性](theme-readability.md)为准：降低刺眼保留材质层次，不改成白板；默认风格仅在用户未另定时适用。

新游戏和新制作的全 UI 重构，在批量生成玩家 UI 图片前执行：**按本作主题定规范 → 内置 image_gen 做代表样板 → 主 Agent 自审并修好 → 以选定样板为参考生成整套 → 实际 Cocos 全量复查**。**本页只属于重塑**（见[两个板块](two-boards.md)）；英化不改原美术，只把带中文字的图做成同画风的英文版，见[英化换图](english-ui-rebuild.md#英化只换带中文字的图画风跟原游戏一致)。局部维护沿用本游戏已确认的规范，只处理当前范围；不追溯重做其他已交付游戏。用户当前明确的视觉方向优先。

## 先把主题变成可执行的规范

在本游戏现有规格中建立 UI 美术小节，或保存一份项目级 `ui-style.md`，后续任务引用同一份。主 Agent 依据题材、角色/场景、玩家和已有参考确定设计，不以“高级、好看、不土”几个形容词代替具体要求，也不要求用户先提供色板才能推进。

| 项目 | 本游戏需要确定的内容 |
| --- | --- |
| 方向与依据 | 主题、参考来源、少量明确的风格关键词；UI 与游戏世界如何协调 |
| 色板与用途 | 主色、辅色、小面积点缀色、背景/面板/文字中性色和必要的状态色，记录 HEX 与具体用途 |
| 背景体系 | 普通游戏页面的全屏背景：首页、选关/地图、游戏内、结算与弹窗遮罩；场景题材、明暗、细节密度与留白区；多关卡/多章节是否换背景。开发者可控完整加载页及完整失败重试页沿用[官方 Cocos 加载与重试样式](cocos-loading-screen.md)，不生成游戏主题背景 |
| 按钮体系 | 主动作、次动作、奖励/视频入口、导航/工具按钮的颜色角色、轮廓、圆角/转角、边线和留白；同类动作跨页面保持一致 |
| 图形与文字 | 明亮Q版柔和立体质感（见[明亮Q版画风](cute-casual-style.md)）、纹理/装饰密度、图标画法、字体气质与小屏可读性；标题可更有主题感，动作文字保持易认 |
| 状态 | 普通、按下、禁用、加载、已领/装备/锁定等本游戏实际存在状态的反馈；颜色之外保留文字、图标或形状区分 |
| 排除项 | 本作应避免的配色组合、装饰、纹理和风格混用；明确主题需要的例外及其使用范围 |
| 显示与像素预算 | 最大实际显示尺寸、有效非透明内容/帧尺寸、预期DPR与允许放大范围；首页/加载/Boss大图与小型图集帧分用途，不以整张画布大小冒充主体分辨率 |
| 样板基线 | 生成输入/回执、样板原件路径及 SHA、实际试放记录、自审缺陷/修复和选定版本；整套素材引用该版本 |

默认采用[明亮Q版画风](cute-casual-style.md)：浅色明亮、圆润可爱、柔和立体、有主题辨识度，**严禁大面积深色**（每页深色像素≤15%、平均亮度≥50，用暗部测量脚本量）。配色以 **1 个主色、1 个辅色、1 个少量点缀色**为起点，另配中性色及必要的状态色；这是 UI 角色分配，不限制角色、关卡或奖励图像只能出现三种颜色。主动作清楚醒目，次要动作降低视觉强度，装饰不抢信息。鲜明颜色可以用于重点，不把所有游戏一律做成灰淡、低饱和或同一套青绿配色。

默认避开大面积浑浊黄褐搭配、无主题依据的金边叠木纹、红绿蓝黄同时争抢注意、彩虹渐变、多层描边和厚重黑影。木牌、卷轴、金币边框、黄色/棕色/金色只在主题和用途有依据时采用，控制面积、层次及文字区纹理；不把某个色相一概判为不合格。科幻、雪地、海港、甜品等按各自世界设计配色与按钮造型，不套用上一款的素材或固定 HEX。

默认不使用大块纯色深底控件：深红、深黑、深绿等深色实心按钮、开关、HUD、标题条、卡片和弹窗面板都排除，按下、禁用、已领等状态也不能退回这种样式；浅红整块色面同样不能代替主题设计。优先按题材设计浅色、带轻纹理或装饰的完整图像面；深色只用于细边线和小面积图标点缀，文字不用深色。完整禁止清单和"游玩区≥80%、常驻UI≤20%、弹窗面板≤60%"的空间规则见[明令禁止的UI](cute-casual-style.md#九明令禁止的ui用户-2026-10-20)。不能只把旧深色矩形换个色相就算重做。用户本人明确要求深色场景时可保留真实夜景，但控件仍须单独设计、清楚可读。

按钮继续遵守[完整成图与材质限制](artwork-and-feedback.md#按钮成图与材质限制)：禁止纯平面色块、写实金属/玻璃/镜面反射、刺眼强高光和普通色块叠字；采用柔和Q版立体。固定英文动作、语义图标及背景在同一张 image_gen 图片里一起生成；价格、奖励量等真实动态数据放在动作图外。主题纹理轻量使用，给动作文字、图标和动态信息留出干净区域。

## 每个页面都要有背景

普通游戏页面的背景是必做素材，不是可选项。首页、选关/地图页、游戏内、胜利/失败/结算页都要有贴合主题、**浅色明亮并带轻图案或场景**的全屏背景图（见[明亮Q版画风](cute-casual-style.md)），由image_gen生成；弹窗用半透明遮罩压暗底层页面，面板本身另有底图。上述普通游戏页面的纯色、渐变、空白画布、代码绘制的图形或占位图都不算完成。开发者可控完整加载页及完整失败重试页使用[官方 Cocos 加载与重试样式](cocos-loading-screen.md)的官方原资源、中性底和标准提示/进度，不按游戏主题重新生图；正常游戏页面及局部按钮等待状态不因此豁免。

- **过关、失败、结算、暂停、奖励等弹窗页最容易漏**（常见症状：只有一张卡片面板，四周是纯黑或纯色）。这些页面的面板后面必须是二选一：①游戏画面仍在，盖一层半透明遮罩（透明度约30%–50%，能看清下面的场景）；②专门生成的全屏背景（如庆祝场景、彩带光芒、主题场景）。**禁止**面板后面是纯黑、纯色、全不透明遮罩，或因为切场景/销毁游戏页而露出空画布。美术线在素材清单里给每个弹窗写明"背景方案①或②"，方案②的背景和其他页面背景一起生成。
- **自动测量**：上述普通游戏页面和弹窗截图都跑`scripts/audit_dark_area.py`，它同时量深色占比、整屏纯色占比和四周边缘纯色占比；边缘几乎全是同一种颜色（纯黑/纯色底）就判不合格。
- **游戏内背景不抢玩法**：中间玩法区域降低细节和对比（偏暗、偏虚或留白），主要装饰放在四周；棋子、角色、可点击物与背景要一眼分得开。
- **真实场景层次**：背景要有能认出来的场景、透视、前中远景、建筑体积或光照；单层阴影、重复剪影和大块深色纯色不算完整背景。
- **动态背景按要求做**：用户要求背景会动时，首页和游戏内都要动，弹窗/暂停时也检查；背景计时和本局进度分开，不能只在 playing 状态更新。用缓慢视差、漂移或交叉淡入，避免突跳、露边和挡住操作目标。
- **长屏不露边**：按设计尺寸留出上下余量，用live Canvas尺寸cover/fill铺满（见[长屏处理](reward-entry-and-long-screen.md)），两种手机比例都不露黑边、不裁掉关键内容。
- **重塑**按启动包主题更换普通游戏页面背景；完整加载/重试页仍按官方 Cocos 规则。**英化**：普通游戏页面原来有背景图的不换，背景上有中文字时只把字换成英文；**原来是纯色的页面（含游戏中）必须按原画风重做背景**，可以简单但必须有画面（[页面不能单调](page-richness.md#二每个页面都要有背景含游戏中)）；用户说"按重塑画风重做"后全部按重塑换新背景。
- 多关卡游戏可按章节换背景以增加新鲜感，数量按规格决定，不为凑数量新增。

## 边框、标题牌、角花：内容只放在内框里（防穿模）

来自用户 2026-10-20 的一次返工：以前只检查按钮之间重不重叠，没把标题牌、状态牌和面板的边框、角花一起算，结果标题压在边框上、底部按钮压住角花。以后所有带边框的面板、卡片、标题牌、弹窗都按下面做：

- **美术线出图时就定内框**：每张面板/卡片/铭牌底图，在素材清单里写明**内框**（边框、角花、缎带、流苏以内真正能放内容的区域，用占图片宽高的比例写，如"上 14%、左右 9%、下 16%"）和**装饰区**（每个角花、缎带、挂饰的位置）。内框留白要够，装饰再漂亮也不能吃掉内容区。
- **标题牌只有两种放法**：①放在内框里面；②要压在边框上的缎带标题，必须和面板一起画成一张图（生图时就留好标题位）。不能在运行时把一个标题牌叠到边框上。
- **组装线摆放时**：标题牌、状态牌、文字、物品展示区、价格、按钮，全部放在内框里，距内框边至少 8 像素，不碰任何角花和装饰，彼此不重叠。展示区（如商店里的商品、皮肤、飞毯）按内框可用空间给足，宁可缩小装饰、加高面板（不超过弹窗面积上限），也不压边。
- **布局从游戏里读**：弹窗打开时用 dump_ui 读一次，`extract_ui_layout.py` 自动找出面板、内框（面板用九宫格图时按九宫格边距算，没有时估一个并标 `safe_estimated` 交 GPT 看）、装饰（角花、缎带、越过边框又没字的图）和放在上面的全部内容。面板最好用九宫格图，内框就是准的。`audit_ui_coverage.py` 会查：内容是否越过内框、是否压到装饰、彼此是否重叠（门禁 UI-03、ART-05）。
- **按最终状态检查**：最长英文、最大数字、已领/锁定/装备等状态、按钮按下放大、入场动画结束后的位置，都要在内框里。GPT 看总览图时专门看一圈边框和四个角。

## 先做样板，通过自审再扩展整套

1. 从本游戏实际控件中选一组能代表风格的样板，通常包含主按钮、次按钮、奖励/视频按钮、一个工具图标、一个弹窗或面板，以及一张游戏内全屏背景（样板按钮要放在这张背景上一起检查）。按实际功能裁剪，不为凑样板新增广告、商城或其他玩法；必要的状态变体一并试做。
2. 用内置 image_gen 生成样板，提示词明确本作色板/角色、轮廓、材质、准确英文、语义、透明与裁切安全区，并带可用的主题参考。样板本身遵守完整按钮成图规则，不能用色块、CSS/SVG/代码绘图或空皮叠字代替；本规范文档不等于已生成样板。
3. 主 Agent 查看样板原件，再导入真实 Cocos 的代表页面，以计划显示尺寸放到实际背景和动态文字旁检查：是否符合[明亮Q版画风](cute-casual-style.md)（截图跑暗部测量：深色像素≤15%、平均亮度≥50）、是否清晰（有效帧达到目标像素预算、默认UI原图至少为最大设计显示尺寸2倍、无像素感/锯齿/毛边，见[清晰度硬规则](artwork-and-feedback.md#清晰度硬规则禁止低分辨率像素风和粗糙边缘)）、配色是否协调、主次是否清楚、纹理是否干扰、图标/字是否易认、边线/留白是否一致、透明轮廓及状态是否完整。文字核对按当前环境 OCR 分流，整体审美由主 Agent 判断。还要实际走首页→玩法→胜败→重试/返回，确认背景未被地形或面板遮住、核心动作可见且可触控；两种比例读回CSS/Canvas backing/DPR、帧与纹理尺寸，检查contain/cover、有效透明边缘及默认/按下状态。Boss等最大展示位必须试放；官方加载/重试页仍按[官方 Cocos 加载与重试样式](cocos-loading-screen.md)查看当前实际帧、官方资源比例与可操作 Retry，不因呈现例外省略实际查看。图集间距靠排布/画布解决，不能通过过度缩小主体牺牲清晰度。艺术显示与碰撞/计分几何分别验证。未形成可用样板时先优化，不批量扩散问题。
4. 记录选定样板和自审结果后继续整套生图，**样板阶段不停下等用户**；整套美术完成并接入后，按[四个阶段](stage-flow.md)在阶段 2 统一交用户试玩验收。后续调用使用工具实际支持的图像参考方式携带选定样板，复用同一色板、按钮体系与图标/文字方向；仅在提示词写“同风格”而未提供可用基准，不算完成风格继承。新页面和新固定状态也从该基线扩展。
5. 样板可直接进入最终素材，不为留流程重复生成。整套生成仍逐项检查色彩角色、轮廓、边线、字体和装饰密度，偏离者重绘/优化；如果修改风格基线，更新规范与版本并复查受影响素材，不静默混用两套。

面板按实际内容收紧，主要按钮按看得见的图片大小（不是命中框）保持足够比例，避免大容器配小按钮和大片无用留白。多类提示同时出现、场景里的图标浮到弹窗上、提示自动退场，按[重叠与空间检查](full-visual-review.md#重叠提示寿命与空间占比)在实际运行中检查。

## 接入现有视觉巡检

按[全量视觉巡检](full-visual-review.md)在两种适合游戏方向的手机比例检查全部页面及条件状态，覆盖关闭/返回/音量等小控件、弹窗/卡片/HUD及固定状态变体。对照本作规范与选定样板检查主次、实际背景上的可读性和整套一致性；发现偏色、材质漂移、装饰过量或新旧风格混用，修复并同位置复查。

不新增重复检查编号或用脚本自动判审美。已有 `ART-01` 的 `ui_scope_and_inventory` 关联本作规范，`imagegen_assets_and_bindings` 关联样板原件/回执/SHA和整套引用，`page_state_visual_review`、`defects_and_rechecks` 记录实际一致性检查及修复。未完成规范、样板自审或整套复查时，不把新制作的美术阶段填通过；这些记录不替代原图/实际页面、触屏、手机或真实 IAA 验证。
