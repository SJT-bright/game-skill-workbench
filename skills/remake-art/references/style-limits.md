# 画风：跟启动包走，只守禁止项（重塑，用户 2026-10-27/28）

用户 2026-10-28 决定：美术规则**只写负向约束**（哪些不许出现），不写任何正向画风要求：不要求明亮、不要求Q版/可爱、不要求糖果色、不要求光泽、不把胶囊按钮当风格要求、不规定颜色固定含义、不设亮度下限（以前的"整屏平均亮度 ≥ 50""亮度舒适"一律取消）、不要求"丰富/华丽/精致"的样子。画风本身来自启动包 `ART_DIRECTION`（用户 2026-10-28：重塑美术跟随启动包设计）；没有启动包时由 AI 结合题材自定。

旧的启动包规范模板里写着 "bright cute art"，那不是本 Skill 的要求：某个启动包自己的 `ART_DIRECTION` 写了什么画风就按它做，本 Skill 不另加、也不强制任何画风。

## 〇、画风禁止项清单（只查负向，用户 2026-10-28）

任何画风都不许出现下面这些；启动包和任何 AI 都不能推翻，只有用户本人对某个游戏明确要求时例外。启动包 `ART_DIRECTION` 和这里冲突时只改冲突的那一点，并在项目记录里写明哪一条、怎么改。

| 不许出现 | 具体指什么 | 怎么查 |
|---|---|---|
| **深色/近黑的文字（尤其深色粗字）** | 字的填充色是深青、深绿、藏青、深蓝灰、深棕、深灰、黑这类深色（L* < 50）；粗体、加描边/阴影或 iPhone 上 ≥16px 的深色字一律不行。深色只可以出现在描边和阴影里 | `dark_bold_text`、`dark_picture_text`、`dark_green_text`，`art_check.py` 的"深色粗字（永久禁止）"行（[永久禁止深色粗字](page-richness.md#永久禁止深色粗字用户-2026-10-23两个板块所有页面游戏中-hud-也算)） |
| **特别密集的文字** | 字距/行距过小、字和字挤成一团、一块区域塞满字 | 位图数字的字距由 `negative_spacing`、`font_advance`、`font_advance_rendered`、`glyph_overlap` 拦；其余没有自动检查，看图判（`visual_verdict`） |
| **特别细的文字** | 细线字、发丝一样的描边、没有描边/阴影/粗体的细字，在手机上看不清 | `plain_text`、`small_text`（iPhone 上小于 11px）拦一部分；发丝描边没有自动检查，看图判 |
| **大面积深色、纯黑/纯色底** | 深色大背景、大面板、大弹窗；纯黑或一种纯色铺满；弹窗后面是纯黑/纯色 | `audit_dark_area.py`：L* < 30 的像素 ≤ 15%、一种颜色 ≤ 40%、边缘一种颜色 ≤ 60%、一整块纯色 ≤ 35% |
| **大白板** | 整屏或大半屏的白色/浅灰白板 | `audit_dark_area.py`：`white_block_ratio` ≤ 25%、`white_gray_ratio` ≤ 35% |
| **单色图标** | 黑色线框/剪影图标、整页只有黑白灰 | 看图判 |
| **刺眼的整屏高亮** | 整屏高亮高饱和、荧光色大面积铺满、刺眼的强高光 | 看图判（不设亮度上限或下限的自动阈值） |
| **无层次平涂** | 没有任何明暗和层次的纯平涂几何形、扁平单色块按钮 | `flat_button`、`plain_block_ratio`；其余看图判 |
| **文字压在复杂底图上看不清** | 字直接压在细节很多、对比很强的图上 | `busy_background`、对比度（小字 4.5:1、大字 3:1，`low_contrast`） |
| **按钮/文字被遮挡、穿模** | 字压图标、图伸出按钮、按钮互相重叠、装饰压字、关闭键盖住面板图里的装饰 | `overlap_text_picture`、`overlap_buttons`、`clip_out`、`text_outside`、`audit_ui_coverage.py`、穿模审查图 |
| **位图字母拼句子、字母大小写串（如 HelP / TaP / Pond）** | 用图像模型生成的字母图集做字体：小写字母被画成大写或缺失，引擎拿大写顶替；说明、教学、提示这类句子用了位图字 | `audit_bitmap_letter_fonts.py`（字母大小写指向同一块图、缺字、多词句子绑定位图字体都判失败）；代码里运行时设置的文字看截图 |
| **发灰低对比的配色** | 奶油/米色/浅灰底配灰绿、灰蓝、灰棕字；浅色数字压浅色底；整页颜色明度接近、发闷看不清 | 对比度（小字 4.5:1、大字 3:1）与 `busy_background`；整体发灰看图判 |
| **挤成一团的排版** | 大段说明堆在面板正中央、行距字距过小；步数/关卡/金币/说明全是同一大小同一颜色平铺；文字块占掉面板大半、没有留白 | `small_text`、`font_advance`；整体排版看图判 |
| **主体不突出** | 最重要的信息（关卡、目标、主按钮）和次要说明一样大、一样颜色，没有主次；玩法主体被面板或文字压住、看不出该看哪里 | 看图判：每页先指出“第一眼该看的那个元素”，说不出来就是不合格 |
| **图片模糊** | 低分辨率、放大使用、像素感/马赛克、锯齿毛边、白边黑边 | `low_res`、`audit_image_clarity.py`（[清晰度硬规则](artwork-and-feedback.md#清晰度硬规则禁止低分辨率像素风和粗糙边缘)） |
| **UI 细节太多、颜色太花**（用户 2026-10-28） | 按钮、面板上叠高光条、反光点、闪光星、内发光、多层描边、密集纹理、绳子边、铆钉、宝石、角花、卷草纹；一个功能一个颜色；同一屏 3 种以上高饱和底色。细节只该在主角和封面上 | 脚本量不准，GPT 在截图总览图上判（见下面的[截图总览判定清单](#截图总览判定清单visual_verdict)）；反例和做法见第二节 |

还禁止：发黑发脏的阴影、生硬的纯黑细描边或多层杂乱描边。下面第二节是用户给过的具体反例，都属于这张清单。脚本量不准的项由 GPT 在截图总览图上判定（`visual_verdict`），**只判有没有出现禁止项**，不按"亮不亮""可不可爱""够不够华丽"判，也不另加正向要求。

### 截图总览判定清单（visual_verdict）

GPT 看本版 `make_contact_sheet.py --binding` 生成的总览图时逐项看下面这些（都是脚本量不准的禁止项），出现任何一项就把编号和问题写进 `open_issues`，`verdict` 不能填 `pass`：

1. 字太深、太密、太细（深色粗字、挤成一团的字、发丝描边）。
2. 单色图标（黑色线框/剪影）、整页只有黑白灰。
3. 刺眼的整屏高亮、无层次平涂。
4. 整体发灰低对比、挤成一团的排版、主体不突出（说不出第一眼该看哪个元素）。
5. **UI 太花（用户 2026-10-28）**：按钮或面板上有高光条、反光点、闪光星、内发光、多层描边、密集点状/条纹纹理、绳子边、铆钉、宝石、角花、卷草纹；同一屏按钮一个功能一个颜色；同一屏 3 种以上高饱和按钮底色。主角和封面上的细节不算。

`observed` 里写清每一项看过哪几张图；只判有没有出现，不评价好不好看。

## 一、画风跟启动包走

- **风格来源**：以启动包 `ART_DIRECTION` 为准（主题、角色、场景、配色、提示词照用），题材与核心玩法物件只用来补它没写到的部分。写实、扁平插画、像素、手绘、厚涂、低饱和、夜景、暗色调题材都可以，只要不碰上面的禁止项。
- **不混用几套风格**：先在[UI规范与样板](ui-style-and-samples.md)里出代表样板，选定后整套按它生成；不能一组按钮几种材质/字形、图标几种画法、字体风格混杂。
- **生图提示词**：写本游戏自己的风格描述（来自启动包），**不要默认加** bright / cute / candy / glossy / kawaii 这类词，除非这款游戏的启动包本来就这样写。
- **亮度**：不设亮度下限，也不要求"亮"。只禁大面积深色和纯黑、纯色底，也禁刺眼的整屏高亮。
- **可读**：不许字和背景分不清、可点的东西和背景混在一起、背景比玩法物件还抢眼。

**空间规则（硬指标）**：

- **游戏中，玩法区要占屏幕 80% 以上**：常驻的 HUD、按钮、摇杆、信息条加起来**不超过屏幕面积的 20%**。只放玩这关必须的信息（通常：关卡/分数一条、暂停、1–3 个道具或操作按钮）；其他的收进暂停页或首页。
- HUD 按用途**成组**放在屏幕上边一条和下边一条（或两角），组与组之间留空隙，**互不重叠**；屏幕中间区域不放常驻 UI。
- 教程/提示气泡小而短：一句话、放在不挡操作目标的位置，做完动作或几秒后自动消失（见首关教程（重塑包 remake-onboarding 板块，英化包不含））。
- **游戏中打开的弹窗**（暂停、设置、复活、试用、奖励等）面板**不超过屏幕面积的 60%**，四周能看到半透明遮罩下的游戏画面。内容多的商店/收集/皮肤页做成单独的整页（有自己的主题背景，从首页或暂停页进入），用分页或滚动，不做成盖满屏幕的白板弹窗。

**怎么检查**：

- 布局数据**从运行中的游戏自动读出，不手填**（用户 2026-10-21）：在 Ego Lite 里用 `chrome_touch.py` 的 `{"type":"dump_ui","screen":"play_9x19","kind":"gameplay"}` 把首页（kind home）、游戏中、每个弹窗（kind popup）在两种比例下各读一次，再运行 `extract_ui_layout.py <这些 dump> --out docs/ui-layout.json` 生成；`audit_ui_coverage.py` 会按 dump 重新提取比对，手填或改过的布局直接拒绝。自动判断错了（比如把棋盘当成 HUD、主按钮没认出来）只能在 `docs/ui-layout-overrides.json` 里标注 exclude/include/primary/label/role，不能写位置。 若HOME入口需经过关联页，可在同文件用 `home_entry_pages: ["实际screen ID"]` 显式声明；先实际导航确认可达。关联页须有实际按钮dump，并与HOME的CSS宽高和DPR完全一致，不能拿别的比例或任意页面代替。生成的 `home_entry_sources` 列出来源及哈希供复核；配置声明不证明路由可达。`scripts/audit_ui_coverage.py` 量面积、重叠和压边框（门禁 ART-05、UI-03，见[防穿模](ui-style-and-samples.md#边框标题牌角花内容只放在内框里防穿模)）。
- 每个页面和弹窗的截图跑 `scripts/audit_dark_area.py`：除了深色，还会量**大块白色/浅灰**（white_gray_ratio、white_block_ratio）和**大块单一纯色**（plain_block_ratio），超标就不合格。
- 文字是否太深/太密/太细、图标是否单色、是否条理清楚，脚本量不准，由 GPT 在截图总览图上按第〇节判定（画面结论 `visual_verdict`）。

## 三、页面布局：货币在最上方、功能按钮集中在下方、图标为主（用户 2026-10-23 修改，试玩版也严格执行）

用户给的反例：首页把 SOUND、WARDROBE、WORLD MAP、MISSIONS、REWARDS、HOW TO PLAY、SHOP ALBUM、TRY THE MECHANICS 做成一堆大文字方块，挤在屏幕中下部；另一款把 8 个文字按钮叠成两列堆在下半屏；还有一款把生成的按钮和白色占位方块混在一起。玩家看着难受。

用户 2026-10-23 又给了一张反例（Hazel's Shelf Scramble 首页）：**金币栏（coin 0 / 道具 1）放在屏幕正中间**，地图图标在中间偏左、皮肤图标在中间偏右、帮助和视频图标分别挤在左下角和右下角，四散在各处，中间一大片空白。该反例保留顶部资源栏与清晰分区的要求；首页功能布局以 2026-10-24/25 的[固定尺寸、两侧入口与动态主页](mobile-button-size-and-home-layout.md)为准。中部两侧有目的地分配入口，不等于把按钮无序散到四角；包括试玩版在内按下面的更新分区执行：

**只有主要功能用文字按钮**：开始/PLAY、下一关/NEXT、继续、主要领奖这类，**一个页面最多 2 个**，大而醒目，但宽不超过屏幕 70%、面积不超过屏幕 8%。

**其他功能一律用图标按钮**：设置（齿轮）、声音（喇叭）、商店（购物车/金币）、衣柜/皮肤（衣服）、地图（地图/旗子）、任务（清单）、首页礼盒（10 帧动画的礼物盒）、签到（日历）、玩法说明（问号）、收藏（相册/星星）、加桌面（小房子）、个人主页回访（人像）。图标一眼能认出的不写字；容易混淆的在图标下面配**一个小单词**。图标尺寸按[固定按钮尺寸](mobile-button-size-and-home-layout.md)执行；旧的单图标 2.5% / 100×100 上限不用于把当前已要求放大的图标缩回去。不做大文字方块、不做一排排同样的文字格子。

**首页布局（硬规则）**：

| 位置 | 放什么 |
|---|---|
| **屏幕最上方一条** | **货币**（题材货币）、体力、关卡进度，放在顶部资源栏里（顶部资源栏（重塑包 remake-levels 板块，英化包不含））。**货币、体力、加号购买按钮永远在屏幕最上方，绝不放在屏幕中间或下面**；右上角给平台胶囊留空 |
| **最上面一行的左上角** | 设置（和声音）按钮，和货币栏在同一行；不放到平台胶囊下面那一行（用户 2026-10-28） |
| 上半屏到中间 | 大标题、按玩法设计的会动的封面：跑酷就是一段正在跑的画面，抓娃娃就是一台能互动的机器，不一定有主角站中间（[首页按玩法设计](home-by-gameplay.md)，用户 2026-10-28）。签到、礼盒、地图、皮肤放在中部左右两侧，左右各至少一个，不遮住主视觉。主角与标题待机动画按[动态主页](mobile-button-size-and-home-layout.md#动态主页主角与标题待机动画用户-2026-10-25) |
| 中下部 | 居中一个 PLAY 主按钮（可再加一个主要文字按钮） |
| **最下面一行** | 只放主页回访、加桌面两个平台入口（用户 2026-10-28），其他入口都放中部两侧。不为填位置新增功能（排行榜、更多游戏、分享仍按禁用规则处理；签到是重塑必备入口，放中部两侧，见经济板块（重塑包 remake-economy 板块，英化包不含）） |

按钮之间互不重叠；**首页所有按钮加起来最多占屏幕 40%，不能超过 40%**（用户 2026-10-23 由 30% 放宽到 40%；这是上限，不是要做满；标题、Logo、封面图不算按钮）。**首页一定要有大标题（宽度至少屏幕的 55%，放在上半屏）和封面画面**（主角、配角、场景、道具组成的画面，或正在动的玩法画面、可互动的机器，不是按钮的图至少占屏幕 15%；画法按启动包）：首页的大部分画面留给标题和封面。游戏中的 HUD 只放在上边一条和下边一条，不放在屏幕中间；游戏中的货币也在最上方。其他页面（选关、商店、皮肤等）有货币时同样放在最上方。

**试玩版不能出现开发用文字**："PLAYABLE PROTOTYPE""PLACEHOLDER ART""PLAYTEST LAB""All 72 layouts are reachable""TRY THE MECHANICS"这类文字一律不显示给玩家；测试入口给测试工具用，不做成玩家按钮。占位版也要按最终布局摆：次要功能用**图标占位**（圆形底 + 简单图标），不要用写着功能名的大方块。美术完成后不能留任何占位方块，不能生成按钮和白色占位块混用。

**怎么检查**：首页用 dump_ui 读出（kind home），`extract_ui_layout.py` 自动认出主按钮和每个按钮有没有文字（认错了在 overrides 里标 `primary`/`label`），`audit_ui_coverage.py` 会查文字方块、按钮大小、设置是否在上角、货币/加号是否在最上方、中部两侧入口与下方图标组是否符合当前分区、是否重叠、全部按钮是否超过 40%；重塑（`docs/board.txt` 写 remake，或没写）另按 2026-10-28 新分区拦：设置不和货币栏同一行或不在左边（`home_zone_settings_row`）、PLAY 下方有主页回访和加桌面以外的入口（`home_zone_below_play`）、签到在下面一排（`home_zone_checkin_bottom`），英化不查这三项；`audit_top_bar.py` 查每个页面上货币数字（和旁边的货币图标）都在屏幕最上方（`currency_only_at_top`）；`audit_dev_text.py` 查开发用文字（美术完成后加 `--final` 同时查占位图）。两种手机比例都要读。GPT 在截图总览图上再看一遍是否紧凑、清楚，并核对 `auto_notes` 里自动判断的内容。


**动态主页（用户 2026-10-25）**：本轮涉及主页封面时，按[主角与标题待机动画](mobile-button-size-and-home-layout.md#动态主页主角与标题待机动画用户-2026-10-25)设计与组装；按钮保持稳定，观察实际循环和运动两端，不以静态截图代替动画确认。

## 四、怎么用、怎么查

- 美术线在[UI规范与样板](ui-style-and-samples.md)阶段把启动包 `ART_DIRECTION` 落成本游戏的风格方案（题材、材质、配色、按钮做法都照启动包），先出样板，放进真实 Cocos 截图看有没有碰禁止项，再铺整套。
- 每个页面截图跑 `remake-core/scripts/audit_dark_area.py`：只查禁止项——大块深色（L* < 30 的像素 ≤ 15%）、纯黑/纯色底、大白板、大块纯色。没有亮度下限（2026-10-28 起脚本也不再提供 `--min-avg`；报告里的 `avg_lstar` 只是参考数字，不判通过与否）。
- 文字是否太深/太密/太细、图标是否单色、整体是否刺眼或无层次，脚本量不准，由 GPT 在截图总览图上按[第〇节](#〇画风禁止项清单只查负向用户-2026-10-28)判定（`visual_verdict`），只判有没有禁止项。
