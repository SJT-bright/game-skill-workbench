# 六标准广告节点贯穿重塑与英化制作

用户2026-11-11要求两套流程都必须包含结束、主页、永久皮肤、体力、局内道具、周期试用六类，新增UI必须在制作前联动美工并适配本游戏。旧版“已有扩展凑够6即可停止”的口径在本轮被替代。额外广告循环可保留，但不占标准六类名额。

## 两条制作路线

| 节点 | 重塑 | 英化 |
|---|---|---|
| 开工 | 写项目规格并运行当前tiktok_finalize init，记录六类标准合同 | 中文原版内部基线及盘点后对工作副本运行当前init，默认六类是英化固定制作范围 |
| 逻辑 | 玩法阶段盘点并设计六类依赖/真实作用，占位只用于内部玩法验证 | 第2阶段用现有零件补齐六类；保留核心玩法、关卡和原画风，不把新增外围系统当作新玩法创新 |
| 美工 | 第4阶段按已定ART_DIRECTION制作广告新增页面和状态 | 第2阶段先把原页面与六类新增UI统一定版、首件及批量制作；第3阶段只集成同版候选并处理实际剩余问题 |
| 正式试玩 | 六类源锚完整，新增UI当前局部检查完成；不要求此时提前伪造最终运行回执 | serve_preview/handoff_preview正式分支同样检查；中文原版、内部和draft仍可继续工作 |
| 写包/最终交付 | 两写包入口及精确ZIP检查调用同一ad_standard_six门禁 | 同一门禁，必须六类运行观察对应实际Native；prepare_delivery沿用正式writer证据 |

第一次完整制作不能沿用旧init来绕过。当前init及新项目自动标记写 `ad_standard=strict_six_standard_families`；已在旧合同下交付的项目仅做无关局部维护时不补整套。明确要求六类迁移时运行当前init或建立六类清单，继续本流程。读取旧包不改原件，也不能宣称它已经通过新六类。

## 施工顺序

依照[生产依赖与共享批次](production-plan.md#英化制作的依赖顺序)。开工先列齐六类的真实作用、入口和全部画面状态，共用存档/发奖、皮肤/道具临时权益和数值接口先定；美工规则与布局在接线/选图前加载，代表首件后统一制作原有及新增素材。代码与已定稿素材可独立推进，合并后按真实需要构建、连续采集和验证；不在美工完成后才开始诊断广告，也不按六类各自重走一遍整套流程。

## 六类与业务作用

1. 结束：复活与结算双倍整体1；两屏，每屏一个视频按钮，免费放弃可立即操作。
2. 主页：5B/30分钟礼盒、转盘与七天签到双倍齐全整体1；转盘不重计，勾选默认双倍可取消免费领基础奖励。
3. 永久皮肤：整体1，至少10款，主角皮肤或无主角的地图/棋盘主题；60%广告款、稀有度、单件一种永久获取方式按皮肤和经济Skill。
4. 体力：整体1，真实开局扣除/自然恢复/存档，广告+3，装不下不播。
5. 局内道具：所有类型整体1，实际改变本局，不只发一个库存数字。
6. 周期试用：每完成3局后局间自愿看广告用皮肤/道具，临时权益不改永久进度；旧无尽皮肤30分钟规则保留。

按表顺序核实并汇总全部缺口，按施工依赖实施；候选先回看真实函数与按钮，不重复安装已有系统。离线、任务或其他扩展单列 `extra_count`，不能补上缺的标准类。逻辑用[广告Skill](../../ad-boost/SKILL.md)现有模块和assemble工具，广告SDK仍用同一平台RewardedService。

## 广告UI制作时真实调用美工

排版、选图、生成图之前先读同包[美工Skill](../../remake-art/SKILL.md)及[新增界面制作](../../remake-art/references/new-feature-ui.md)，然后执行：

```sh
python3 -B "<skills>/ad-boost/scripts/art/skill_link.py" prepare --project "<工程>" --board localize --reference "<原游戏实景或同类素材.png>" --out "<本轮新的上下文.json>"
```

重塑写 `--board remake` 并读取项目ART_DIRECTION；英化必须用真实原游戏参考，不能把上一款按钮当新游戏风格。prepare会读实际美工文档/修订与画风文件，缺文档或画风源即不就绪。它只准备制作输入，`ui_complete/visual_passed=false`，不能凭这份JSON写UI通过。

先定入口/返回、底板、标题、字形、图标、奖励显示、主次操作和状态。按实际显示槽制作，PNG尺寸不决定节点宽高；图标与勾选框跟等比后的可见底板定位，不能跟较大的触摸外框。正文可换行，固定短词用本作字形；最长奖励、默认/禁用/加载、取消提示、窄屏和长屏都留在本轮范围。不得把通用圆角/哑光等模板写成所有游戏的正向画风。

在既有pages.v1登记六类实际页面、广告按钮与角色；用原page_registry派生screens。把本轮新增/受影响状态接到既有visual-slots/capture-plan，保持视觉ID与采集ID准确映射。先接一件代表品，查看真实Cocos画面与输入，再批量复制；仅查本轮新增和确受影响状态，原有效记录沿用。

```sh
python3 -B "<skills>/ad-boost/scripts/art/skill_link.py" check --project "<工程>" --board localize --dumps "<真实采集目录>" --production-only --first-piece-case "<本轮visual case>" --out "<新的局部输出目录>"
```

check调用原art_check和首件checker；没有dumps、实际未运行或发现问题都不能写通过。六类清单中的ui只连接现有page_ids、visual_case_ids和原局部报告路径，不另造一份全量美术回执。共享门禁核当前原始采集可沿用状态，并重放同一受影响范围的生产检查；不会把读过规则、模板存在或一张效果图当成Cocos制作完成。整体画风和实景观感仍由Agent逐张看图判断。

## 同一份清单与同一处门禁

`docs/adboost/ad_nodes.json` 同时登记六类业务、稳定奖励事务、源锚与本轮UI范围。`qa/ad-nodes-runtime.json` 绑定当前运行器、原trace与构建依赖，`build_directory`是项目内实际Native目录。最终包会逐一核这些依赖在本次Native/ZIP中的相对路径与字节；不接受另一个构建或QA模拟文件。

`ad_nodes.py audit/plan/check` 输出标准数、扩展数和总数，只有标准数6、必备无缺且证据有效才达标。正式试玩用trial阶段(六类接线+本轮新增UI)；最终写包用writer阶段(再加六类运行与实际Native绑定)。两写包入口、check_package、prepare_delivery共用package_gates/ad_standard_six，缺工具/清单/当前观察或新增UI证据均阻断，当前AI定位具体问题修复后回原步骤继续。

完整美术总回执已经撤销，不能重新要求全图指纹或全页面重新签收。现有轻量art-check-record与本轮实际局部检查各司其职，旧正式试玩记录按原工具沿用。内部预览用于继续制作，正式同版H5与最终包交接沿原计时和服务工具；本次只更新Skill时不自动改任何已完结游戏。
