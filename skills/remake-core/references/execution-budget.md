# 执行节流（省Token硬规则）与用量复盘

**持续执行与进度汇报（2026-10-25纠错）**：用户已授权的开发、完整验收或出包，不按固定分钟、一次修复、固定测试数量或一次预览更新切成等待“继续”的回合。修好一项且局部回归通过后，只在 commentary 汇报进度，并在当前任务继续下一项；“整体未完成”是继续工作的状态，不是 final 收尾理由。省Token的检查点/回合提醒只用于保存进度，不构成停止授权。仅到用户明确要求的交付终点、既有必需人工确认节点、用户停止、工具安全停止或确需外部输入且独立工作已尽时才结束；如有真实限制说明具体原因，不让用户用“继续”代替内部调度。新聊天仅按已授权的阶段接续规则创建，不自动扩大跨聊天操作。


**范围裁定（2026-10-24）**：先按[检查范围、历史回归与停止条件](../../cocos-game-check/test/references/testing-scope-and-stop.md)选档；本页的全量步骤用于相应完整验收，局部维护只执行受影响项。质量与真实证据要求不变。

来源：2026-10-18三款游戏（玛雅神庙探宝、云朵小兔、热气球旅行）的逐次调用审计：三款共3,409次模型调用、约7.05亿累计Token；98.5%是重复读入的历史，输出只占0.4%；每次调用平均携带约20.6万Token历史，总控一条线占25%–33%。**消耗 ≈ 调用次数 × 每次携带的历史**，所以要同时减少"无新信息的调用"和"每次的历史长度"，只要求回答简短没有用。

口径：历史审计数字不是每款游戏的预算；缓存比例不是浪费率，等待/相同命令计数只是排查线索；累计Token不能直接换算账单或订阅额度，费用、额度、生图成本分别记录。

本页规则对所有线生效，优先于其他页面中"多查一遍更稳"的倾向；用于减少没有新信息的重复工作，不降低交付门禁、原始证据审核或用户当前指令。

## 1. 不轮询：等待时什么都不做

审计证据：打包线35次相同的50秒sleep（约896万），用户提醒后仍继续21次；总控78–86次等待聊天；协调/等待类调用约占一个项目的20%。

- 任何线依赖未满足时：在分工表写一次`等待：等什么｜谁交付｜满足什么条件恢复`，先做可做的独立工作；可由当前工具等待的构建/测试继续受支持的有界等待，不把普通依赖等待当作用户需发“继续”的节点。只有确需外部输入且无独立工作时才明确阻塞。禁止 sleep→读同一进度/日志→sleep 循环，禁止为"看看进度"调用模型。
- 总控需要等子会话时：对全部进行中的子会话发**一次**等待，用工具允许且符合平台沟通要求的最长超时；返回后只处理已完成、新失败或输入变化的那几条，没有就直接再等；**两次等待之间不读进度文件、不查日志、不发消息、不写说明**。总控保持很小（见第2条），每次醒来的成本才低。连续等待无事件时检查任务是否仍有效、是否有明确失败或可做的独立工作，给必要进度并继续受支持等待；不设“10次后结束等继续”的阈值。只有真实外部阻塞才说明并结束。
- 已完成的线**休眠**：只有测试发现了它负责的问题、收到跨领域请求，或用户在该会话里提修改，才处理；要追加的事攒成一条消息发。不发"确认/同步/冻结通知"类消息。
- 长批次自己写检查点、逐局结果、有效数和失败/完成摘要；模型只在启动、出现新失败、批次结束时介入，期间不读日志、不汇报进度。

## 2. 总控只调度，保持很小

审计证据：总控自己跑了190–198次命令，看图、改代码、审代码，历史涨到35–45万，是三款里最大的单线消耗。

- 总控只做：建子会话、发开工指令、等待、读交接与分工表（只读这两类小文件）、裁定、转达跨领域请求、更新分工表。
- 总控**不**跑命令（读分工表/交接除外）、不看图、不改代码、不审代码、不复查任何线的产物。需要判断代码或画面时，派给负责线并要它返回结论。
- 最终验收负责人是锁定后的"最终验收"（Codex，见[测试分工](session-relay.md#锁定后的测试分工)）：它看原始报告、总览图和证据图，不只接受子线一句结论；证据不足就退回补齐，不以节流为由跳过最终审核。总控不兼任。
- 实现线的自查只是输入，不是最终签收：最终签收由**视觉与测试线**（GPT，见检查节奏）和打包前的固定门禁完成，不由总控重做。

## 3. 阶段边界与回合提醒

- 回合提醒：总控40；组装、平台、视觉与测试每个会话80；美术、文案、音频、打包每个会话50（音频通常远用不到）。到提醒值后，**在最近的自然节点**（一批素材完成、一个功能完成、一次修复完成）写交接并按会话规则续开，不在任务中途机械切换——新会话首次读入也有成本。已发生自动压缩、开始忘规则或改坏已修内容时，立即交接。
- 计数口径：本机可读用量日志时，以去重后的递增用量记录为准（不是用户消息数、工具子调用数或账单请求数）；读不到日志时数自己的模型回合作提醒，两种口径不混比。
- 交接只留目标、准确路径与当前指纹、已做/待做、活跃问题与负责人、证据路径和恢复命令；新会话只读这些及本步需要的原件，不读旧聊天。

## 4. 定位读取和短输出

审计证据：50–54次工具输出被截断，单次最长3–4万字符，进入上下文后被之后每次调用重复携带。

- 先限定当前游戏和目录，默认避开node_modules、虚拟环境、原始归档和证据快照树，直接相关才进入。
- 读代码先`rg`定位，再读需要的行范围；不通读压缩bundle和未变化的大文件，不重复读未变化的文件。
- 命令和脚本正常时只返回：退出码、数量、改了什么、证据文件路径；失败时最多3个已定位根因+附近日志位置。目标每次约1,000 Token以内，完整日志、JSON、报告写入文件，不cat进对话，也不丢失真实失败记录。
- 已安装工具正常且版本未变时复用环境盘点；截图只看当前受影响的页面/状态，不重复载入旧图。

## 5. 状态只有一个权威入口

- `docs/progress.md`的分工表是唯一当前状态：版本/指纹、各线状态、活跃缺陷与负责人、等待条件、下一事件、证据路径。更新时直接覆盖旧状态；历史只追加到`docs/log.md`，旧待决/旧下一步标替代关系，不与当前结论并列。
- AGENTS保留稳定约束和导航，交接保留本线契约，不复制多份pass表。接收原档只盘点一次，指纹变化才重做相关盘点。

## 6. 复测必须有触发原因，证据按依赖复用

审计证据：冻结v1→v4反复重跑整套；"54项pending不等于54项未执行"却被当作待测。

- 每次准备复测，先写四项：**哪个输入变了｜影响哪些检查｜旧证据为什么不能用｜通过后做什么**。写不出变化或未决问题，就引用已有证据，推进下一项。
- 用[工作流工具](workflow-tools.md)保存检查输入快照并比较：依赖覆盖源码/资源清单、检查工具与版本、环境/参数/种子与证据层。输入未变只是"可复用候选"，仍需确认原始结果通过、证据有效；工具不会写pass。缺失输入、未知覆盖、新检查或条件变化不能跳过。
- 一次修复可能影响多个状态：改按钮核触控传播/弹窗状态，改奖励核所有消费者，改完成条件/碰撞核相关难度统计；只复测受影响的部分，不全量重跑未受影响部分。
- 同一失败原样重试最多2次；第3次前必须换方法或归因，普通缺陷不直接转交用户。Web、SDK替身、目标Runtime、物理手机、真实IAA、平台接受分别记录，不跨层复用。整包SHA证明交付身份，不取代检查依赖。

## 7. 先做高风险可玩样板，再铺量

审计证据：共享图片组件缓存与图层、奖励保存失败与真实兑现、复活第二次死亡、音乐"假播放"、冷开加载失败、包体超限、登录适用性、物理单位换算、换图改碰撞宽度——都在铺开后才发现，导致多次解冻重来。

开工后、批量生成美术和铺全部关卡之前，组装线先做一个**可玩样板**并在真实运行中过一遍：

1. 入场确认工程类型：可编辑Creator工程，还是只有编译导出包（走[导出包补丁路线](cocos-runtime.md#编译导出包与预览入口)）；据此定验收输入，不让通用门禁事后再适配。按[Native 启动到首关](cocos-runtime.md#先验证-native-启动到首关)确认 Web 和 Native 都能导出、Native 包结构对，再在浏览器里冷启动到可操作首页并完成首关，做一次加载失败/Retry（不找、不问 TikTok 开发者工具）；在铺量前做，不等锁定后的测试、不出交付ZIP。
2. 首页→玩法→胜败→重试/返回；背景可见，主要动作明确且真实可点。一个共享按钮/图片组件：冷开、关闭后热开、按下/禁用、与动态文字的图层顺序。
3. 按最大展示尺寸试放角色/加载图/大图，核有效帧像素、透明边缘、缩放和预期DPR；两种手机比例看清晰度、背景遮挡和输入坐标。不为图集留白过度缩小主体（见[清晰度硬规则](../../remake-art/references/artwork-and-feedback.md#清晰度硬规则禁止低分辨率像素风和粗糙边缘)）。
4. 一条完整奖励链：完整观看→保存→真实消费者生效；保存失败→同凭证重试不重复发；取消/失败不发。没有该机制写不适用，不为样板新增广告。
5. 复活按[适用范围](../../remake-ads/references/rewarded-revive-and-help-layout.md)先审查/补齐，已有或本轮应补的复活核保护结束与第二次死亡；首关真实启动生命周期；真实首触声音与音量；冷开资源/字体加载失败与重试；官方包体与API/登录扫描。
6. 视觉节点与碰撞/计分几何分开；有物理时先做无变化/上/下三个小对照锁定单位；加速不能关掉参与世界坐标/物理更新的渲染。

样板通过后美术批量生成、关卡铺开，尽量只冻结一次。新需求或真实缺陷可以有原因地产生新候选，保留旧证据身份，不为"一次冻结"隐瞒变化。

## 8. 测试工具先冒烟，长批次交给脚本

- **GUI 测试前必须先跑一键预检** `python scripts/preflight.py --project <工程> [--native-zip <包>] [--screens <截图文件夹>] [--levels <总关数>]`：清晰度、音频来源、中文残留、广告接入标记、触屏写法、包结构、广告位绑定、截图大块深色与背景、关卡抽测清单一次查完，只读它的一页摘要。能被预检查出的问题不进触摸测试轮次。

审计证据：机器人首轮98项97项失败（测试调用了不存在的接口）；打包诊断多次因输出解析失败；1000–2000局批测期间模型反复陪跑。

- 任何新测试工具：先跑1例，再跑5例，输出固定为机器可读JSON，核真实接口、解析和实际业务结果后才跑全量。加速运行先对照原引擎的输入轨迹和结果，固定协议、计时与种子。
- 长批次由脚本自己跑：保存候选指纹、计划/完成/有效数量和逐局记录，每关结束写摘要；依赖与统计协议未变且原规格允许时才断点续跑。诊断用摆位与自然游戏统计分开。
- 原规格要求的批次数量照做，不擅自删减；要改样本量须用户明确同意。长批次绑定冻结副本，依赖变化后写明哪些结果失效。

## 9. 打包最后才进场，且只在用户要求时

审计证据：打包线在候选还在变化时进场，做了10轮业务诊断，又反复冻结重来。

- **每次出包都需要用户说"打包/重新打包"**（用户可在任何会话说，由该会话转给总控），以前的出包指令不自动延续到之后的改动——用户常一次改好几处再统一出包。其他线已完成并冻结输入后才开始。
- 打包线不做业务诊断，失败退回负责线，不以改断言解门禁；公共打包工具可以提前准备一次，但不常驻、不跟随变化中的候选。
- 每轮指定一个当前交付物，历史ZIP保留并标历史；回解后核路径/CRC/逐文件SHA及规定的包后检查。预览更新不会自动更新旧ZIP。

## 9b. 不压垮电脑

被占就开新的、绝不等待（用户 2026-10-23）：浏览器测试/录屏/批量跑关每次在 Ego 里新开独立测试窗口，后台多开，新开前 `browser_slots.py sweep --close` 关掉空了的旧窗口，**每次测试用完马上自己关掉这次开的窗口/空间/预览**（`browser_slots.py close --name <线名>`，所有环节）；只有同一个游戏的构建、音频流水线用 `heavy_lock.py --project <工程>` 放后台排队，不同游戏互不等待；修改攒一批再构建，平时只导 Web、打包时才导 Native；录屏分析加 `--delete-frames`；开工和收尾跑 `cleanup_machine.py`。详见[不压垮电脑](machine-load.md)。

## 10. 预算与阶段复盘

下一款同类游戏的试行目标（不是承诺或停工条件；需求变化、续接与独立审查成本单列）：

| 线 | 模型调用目标 | 平均输入目标 |
|---|---:|---:|
| 总控 | ≤60（含续开） | ≤8万 |
| 组装（玩法） | ≤120 | ≤12万 |
| 美术 | ≤70 | ≤10万 |
| 音频（轻量） | ≤20 | ≤6万 |
| 文案 | ≤25 | ≤6万 |
| 广告/平台 | ≤25–100（按实际系统） | ≤9万 |
| 视觉与测试 | ≤100 | ≤12万 |
| 打包 | ≤30 | ≤10万 |
| **合计** | **450–525（分项相加）** | 按实际调用加权，不预填 |

对照：三款实测平均每款约1,136次调用、每次约20.6万。首轮完成和打包后，用[用量工具](workflow-tools.md#用量复盘)读取调用数、平均/P90输入、缓存/非缓存输入和等待信号摘要，完整日志不进对话；不为统计频繁跑全量日志，也不扫描所有历史。不同工作范围不按总量排名，按可比阶段和完成质量对照；节省比例属于待实测假设，不换算成费用承诺。
