# 通用问题的适用范围与检查重点

实际检查编号、动作和预期只维护在 [known-issues.json](../assets/known-issues.json)，按 [生成与拦截规则](known-issue-checklist.md) 输出当前游戏清单。本页说明如何提炼和选择通用机制；原游戏的对象名称、专属改图、布局位置、奖励数值、玩法调整、时间阈值和事故复盘均留项目，不进入通用执行表。

## 通用化判据

每项必须回答：适用于什么功能、怎样触发、观察什么结果、什么情况下不适用。去掉游戏名称后，另一款同类功能应能直接执行；否则只留项目回归。

- 加载阻塞、文字/图标/按钮重叠、广告完成判断、奖励保存和重复触发，按通用机制检查。
- 个性化的素材、位置和玩法变更只验证当前项目的授权结果；不能据此要求下一款游戏增加同一功能；用户明确要求的通用广告复活审查/补齐除外。
- 运动、几何、拖动和周期奖励仅在实际存在该功能时检查。广告复活按用户通用要求先审查，已有复核、缺少补齐，详见 复活与小型教程审查（重塑包 remake-ads 板块，英化包不含）。其余机制不适用要有源码/界面或用户范围依据，不能为填清单新增功能。
- 今后制作、换皮产出不提供广告跳关，新输入原源码自带也一律按 跳关范围与残留检查（重塑包 remake-onboarding 板块，英化包不含） 同时移除入口、绑定、处理器、广告请求和跳关消费者；以后经手的每个游戏都不得有；这次没有经手的已结项游戏不用回头改。没有跳关不算功能缺项，不为通用 checker 增设必须有跳关的条件；教程跳过、同局复活与免费 Retry/NEXT 分别按真实效果保留。
- 通用条件也不预设实现：运动可由输入、脚本或物理驱动；计时可用游戏时间或现实时间；结果须符合该游戏真实规则。

## 优先检查广告与奖励

先列全实际入口，再逐入口验证以下链路；相同广告位服务多个入口时也不能合并测试。详细动作与后置条件使用统一编号，不另建第二套固定表。

| 重点 | 必须读回的结果 | 统一编号 |
| --- | --- | --- |
| 入口与配置 | 真实按钮绑定正确请求和奖励目标，源/Native/ZIP同版；归属启用状态有依据 | AD-01, AD-05, UI-10 |
| 过程与恢复 | 连点不并发；有等待反馈；无SDK、异常、取消、超时可退出或安全重试；未结束会话不重叠播放 | AD-03 |
| 完成与会话 | 仅明确完成结果发奖；show成功不等于完成；正常前后台往返不丢有效结果，主动离页的旧结果不误奖新目标 | AD-02, AD-04, LIFE-02 |
| 发奖与数据 | 类型、数额、目标、次数准确；领取记录与余额一致；保存重试不重看；写成但读回失败不重复入账 | CLAIM-01, STATE-01, STATE-02 |
| 成功与失败的外观 | 成功后按钮/文字/红点符合领取策略；失败不耗资格，等待遮罩能解除 | CLAIM-02, CLAIM-03, CLAIM-04, CLAIM-05, CLAIM-07 |
| 持久与实际效果 | 关闭重开、刷新/新局、实际使用或即时效果均正确；扣减与交付失败可恢复，独立奖励不互相覆盖 | CLAIM-06, STATE-03, STATE-06, GAME-AD-01 |

领取策略分别填写一次、每日、每局、可重复或带奖励的导航；没有对应功能就不套用。原有免费奖励、通关基础收益和已存库存消费不能被误改为必须看广告。导航任务与视频广告分别验资格。浏览器无SDK时只能检查可达、可退出及不发假奖；真实视频、取消和奖励回流由当前平台/设备另验。

角色/皮肤/武器等获取按 物品获取与递增难度（重塑包 remake-skins 板块，英化包不含） 检查。用户授权递增门槛时逐展示顺序核价格/完整广告次数及比例，移除未授权免费试用或装备旁路；初始物品和合法旧库存单列。配置扫描不能代替实际获取、保存、刷新与进入关卡后的装备检查，项目正反回归接实际打包入口。

“领取成功”按 [领取结果一致性检查](known-issue-checklist.md#领取结果一致性检查) 细查：本次/下次奖励不混、已确认入账不继续报失败、拥有/选中/实际效果与相关缓存页面一致。保存故障与正常跨页/设置操作、周期变化组合检查，旧事务不消耗新目标凭证。原规则、用户变更与旧记录未知状态分别处理，具体事故复盘留项目。

异步查询（平台任务资格、看广告、加载）按 ASYNC-01 检查：**每条返回路**（回调、Promise、两者都来、空结果、只有 complete、reject/抛错）都进同一个单次结算并有可见终态；把 SDK 结果和原超时定时回调**同时扣住**，看实际画面能结束等待、重试能成功；测试替身要能分别用每种方式返回。详见[返回方式和等待出口](tiktok-home-growth.md#返回方式和等待出口写了超时--能结束等待monkey-dash-2026-10-21)。

## 为什么规则写了还会漏（Monkey Dash 2026-10-20、10-21 两次复盘）

同一个"点了没反应"在同一款游戏连出两次。第一次之后规则已经写进 Skill，第二次还是漏了，原因不是没写，而是**写了没人强制**：

1. **规则写成文字，门禁只收 AI 自己填的 true**：例如"等待有上限"只核 `bounded_wait: true`。现在改成要填具体做过的事（扣住定时器后恢复、重试成功），并且要有改坏版本的失败记录。
2. **Skill 自己的示例带着错误假设**：只写了 `({success,fail,complete})` 一种调用写法，代码和测试替身都照着只接 success。示例和替身都要覆盖全部返回方式。
3. **"代码里有超时"被当成"等待一定会结束"**：必须把结果和定时回调都扣住实测。
4. **检查总数掩盖了缺口**：1700 多项通过，也没有一项测 Promise 返回。先看"入口 × 返回方式 × 生命周期 × 玩家看到的结果"矩阵，再看总数。
5. **共用门禁会拒绝，不等于打包脚本调用了它**：现在要用 `test_writer_refusal.py` 实际跑本游戏的打包脚本，证明缺证据时真的出不了包（BUILD-03）。

新机制只要在代码里出现（扫描脚本能找到），就自动要求它的检查，不靠 AI 想起来。

开工时按[重开与触摸输入](../../cocos-game-check/test/references/replay-and-input-checks.md)把本游戏的新机制提前映射成正常/错误或取消/重复/销毁后迟到/重开检查，不等新游戏先出同类事故。重点保留"有效进度跨过等待时间""后台等待""真卡住后恢复""重开后计分和输入"四个对照；具体时间和业务断言留在项目里。

## 其他通用机制

加载和资源检查以真实目标界面可到达为准，不只看HTTP或静态图；排版检查覆盖最长文案、条件入口及等待/错误/已领状态。叠窗、动画和输入按操作归属与当前有效状态检查。玩法和结束条件只核已有或明确授权的规则，历史个性化需求不升级为通用产品要求。

按当前出包路线执行适用门禁：完整制作由打包脚本调用 `check_known_issues.py check --stage pre_scan`，非零停止；已批准成品维护沿用轻量出包路线，不因本页升级完整制作CI。复用同版有效回归，只补改动、失效或有疑点项。`test_writer_refusal.py` 验证的是Skill打包工具的拒绝行为，仅在修改对应writer/门禁调用时运行，不列为每款游戏每次出包必跑。修复已有故障时尽可能保留旧失败、修复通过及正常对照；无旧候选应明确缺失，不能伪造或阻断无关新游戏。项目用例、固定关数和路径不成为其他游戏的硬编码测试。


运动、横竖屏适配及相关反馈，另按 [手机连续状态与帧率检查](../../cocos-game-check/test/references/mobile-motion-state-review.md) 复核实际存在的状态迁移、时间单位、输入退出和末级效果；仍分别记录编译包、真实 Cocos、可信触摸与手机证据。
