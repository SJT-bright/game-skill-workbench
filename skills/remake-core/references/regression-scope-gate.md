# 返工执行范围门禁

适用于正式写包、包级运行与激励回归、最终交付。按游戏实际依赖规划，覆盖皮肤、转盘、地图、玩法、按钮及其它改动。沿用真实通过的原记录，保留原执行时间和原始证据。正式发布前只用本机已接入门禁的入口；不要切换到旧版本、手工启动整套用例或自行改写计划来解除拒绝。

**先核对本轮交付目标。** 用户本轮只要求讨论流程或沉淀 Skill 时，读取已有案例说明问题并更新规则。提到某个游戏、旧测试或交付失败只提供背景。实际检查和交付在用户当前授权覆盖该游戏工作时执行。用户明确暂停或缩小范围后，按最新要求收尾对应操作。

## 先读计划，后运行

1. 固定已经过 Native 标准化的候选、回归适配器和上一版正式 ZIP。需要出包的候选依然按原规则检查启动、资源、已知问题及最终实际归档。
2. 用 `regression_scope_gate.py inspect` 读取实际账本计划。按输出对照本次源码、页面、资源消费者、关卡使用者和共享调用关系。只读检查不会启动浏览器。整包通配、合并脚本变化、版本变化都不能证明某玩法受影响。新增或删除的产物也要有实际归属。遇到 `scope_required` 立即进入下文的修复与续跑流程，由当前 AI 继续处理。
3. 只将真正要执行的检查 ID 与理由写入 `--proposed` 指定的 JSON 对象。需要正式 Native 启动补验时登记 `startup.native.renderer`。`plan` 用现有账本计算所有适用项，核验每个要执行的项都有独立范围，将正式基线、候选、适配器、依赖配置和执行清单绑定到同一计划。沿用项仍在完整覆盖内。
4. 用 `ENGLISH_CHECK_REGRESSION_PLAN` 指向生成的绝对路径，再调用写包器并明确提供同一原交付包。正式入口在启动浏览器前读回计划，回归入口用实际清单再次校验。执行中改计划、改候选、改适配器或换基线都要重新规划。
5. 交付核对复读最终 ZIP 的实际配置、体积、CRC 与 TikTok CLI，核对写包回执的完整用例覆盖和已存在的同版 Native 启动证据。回执缺失、失配或仅有诊断子集时，由当前 AI 找回匹配证据或回到对应写包节点修复、定点补验，再回交付入口复核。

示例使用已准备的 Native，项目、适配器、原包路径按实际填写：

```sh
gate="$HOME/.codex/skills/remake-core/scripts/regression_scope_gate.py"
python3 -B "$gate" inspect --project "$project" --native "$native" \
  --adapter "$adapter" --board localize --policy new
python3 -B "$gate" plan --project "$project" --native "$native" \
  --adapter "$adapter" --board localize --policy new --prior "$prior_zip" \
  --proposed "$requested_ids_json" --out "$plan_file"
export ENGLISH_CHECK_REGRESSION_PLAN="$plan_file"
# 写包器继续用本版原有必填项，并传 --rework-of "$prior_zip"。
```

`inspect` 只是预估，包括缺口和旧配置实际打算运行的用例。`plan` 核准失败没有执行文件，任务继续修复。全量是单独模式 `--mode full --authorization <本轮用户明确要求>`。缺少原包、适配器变化、旧证据无效或用户只说「出测试包」不属于全量授权。用例已经通过且记录仍有效时，仍可复用。没有上一版正式 ZIP 但同版全部检查已有有效记录时，可显式选择 `--mode reuse-only`。该模式发现缺项后交回修复流程，启动证据也只能沿用。

## 修复与续跑

门禁拒绝当前命令后，已授权的检查或交付任务进入 `repair_required`，由当前 AI 当轮定位并修复。优先复读原始证据和实际依赖，补齐缺口并重新核准，回到原来未完成的节点，继续到已授权的检查或交付完成。原有证据足以核对时沿用，确实需要新观察时只补该项。依赖登记、原证据恢复、用例拆分和定点补验按已有授权推进。记录具体缺口、修复依据和续跑结果。

用 `repair` 一次收集可定位的缺口。修复后再次调用，工具重新核对全部身份和原证据，符合范围时直接生成执行计划。每次使用新输出文件保存原始失败过程。

```sh
python3 -B "$gate" repair --project "$project" --native "$native" \
  --adapter "$adapter" --board localize --policy new --prior "$prior_zip" \
  --proposed "$requested_ids_json" --out "$repair_report" --plan-out "$plan_file"
```

| 发现的问题 | 当前 AI 接着完成的修复 | 续跑位置 |
|---|---|---|
| 漏传计划 | 从当前候选和账本生成有效范围计划并传给原入口 | 原来尚未执行的节点 |
| 执行中换计划，或候选、适配器、基线发生变化 | 重新核对当前身份和真实差异，生成新计划，沿用仍有效的已完成结果 | 原来尚未完成且适用的节点 |
| 整包通配、缺归属、合并脚本变化 | 追踪实际模块、资源与消费者，用具体依赖和用例范围替换整包通配，再核准计划 | 受影响的独立用例 |
| 旧执行器混合多个功能 | 拆出可独立执行和判定的单元，核对原断言及必要前置 | 具体功能单元 |
| 测试手势、按钮路径失效 | 对照当前界面修正操作路径与等待条件 | 失败的操作所对应单元 |
| 原始证据文件缺失 | 搜索本项目原证据、交接目录和备份，按哈希恢复。确实无法恢复时只为该独立项补验 | 缺失证据的单元 |
| 最终 ZIP 的交付回执缺失或不匹配 | 核对实际 ZIP、版本和原正式记录，找回匹配的真实回执。确实找不回时，回到对应写包节点修复，沿用有效证据并定点补齐缺项，重新取得匹配回执 | 原正式写包及交付复核 |
| 专项发现产品问题 | 修复具体实现和实际共享依赖，保留失败证据 | 失败项及确实受修复影响的项 |

修复进展包括新查明的调用关系、恢复的证据或实际输入修正。每轮按这些变化重新规划，已有效的项继续沿用。相同输入、相同失败且没有新证据时，先继续诊断原因，避免重复执行同一失败命令。

如果确实缺少只有用户能提供的文件、权限或决定，先完成其余可独立推进的工作，再说明已查到什么和需要哪一项输入。用户明确暂停时，按要求暂停对应工作。范围说明未补、旧脚本粒度过粗、回执路径或版本失配本身属于当前 AI 的修复工作。

原通过项的文件确实已丢失且恢复无果时，在 `check-inputs.json` 的 `evidence_rechecks` 按具体检查 ID 记录 `prior_key`、`reason` 和 `searched_locations` 绝对路径列表。账本复核原文件确实失效后才允许该项补采，使用新的记录 key 保留旧执行身份，已有效的其它项继续沿用。计划绑定整份依赖与恢复声明。

`repair_required` 的 `task_terminal` 恒为 `false`，修复报告没有执行许可。只有 `plan_ready` 中新生成且通过原门禁核验的计划才能启动回归。恢复旧证据时保留原执行时间、原始字节与身份，新的检查结果由实际执行器生成。

## 局部计划按真实依赖判定

每个待跑节点仍需独立的依赖范围、变更理由与许可。待跑项数量恰好等于某个工程的适用项数量，不单独构成拒绝理由；逐项核对真实变化与证据。整包通配、合并脚本未解析、未申请的项目与输入未变项仍按原门禁处理。

## 不把整组当专项

已经独立分项的广告入口、启动场景、前后台恢复和布局状态按 ID 选择。仍以 `@suite` 执行的检查要记录其不可拆分且全部受影响的真实依据。包含不同功能的旧广告结果、存档步骤或全页面按钮巡查不能靠改名当成专项。脚本做不到独立执行时，当前 AI 直接拆开对应流程，或从原始证据证明未受影响项可以沿用，随后继续原任务。

Cocos 合并脚本应追到真实模块与消费者。单纯把整个脚本加入每项，或者把它从所有项删掉，都无法解决范围问题。相关变化没有可核对的模块或资源归属时先补映射。首次迁移旧项目可能遇到需要登记的依赖，保留旧结果，不改原回执身份。

计划和执行约束适用于当前受支持的本机脚本。独立下载的旧版本和任意外部脚本不受这个本机门禁控制；共享发布后应以版本和正式回执核对使用入口。
