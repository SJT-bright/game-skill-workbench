# 已交付后的定点返工与人工快查

适用用户 2026-11-08 的明确要求：同一套 Skill 做出的源码包和测试包已经交付，之后被退回，要求修改指定问题并重新交测试包。它是 `source` / `handoff` 两条主路中的 `returned` 状态，不是重新从中文源码开始。通用依赖和检查记录继续按 [一次通过、按改动复验](incremental-checks.md)。

## 1. 先识别交付意图，沿用已有工作

读取本次用户原话、上一次实际交付 ZIP 和源码身份、指定问题及本次改动清单。收到同事做好的同 Skill 源码和测试包，也按此处理；先恢复随包的节点记录，不因换人、换电脑或重新解包重跑原流程。

**用户明确说“把这处美工改完，给我测试包”即授权本次指定美工按修改结果交付，默认免 AI 美工复验，不再额外问一轮“是否接受美工”。** “改完直接出包”“这几张图按我说的换掉再出包”同义。只适用于已经交付后的本次指定视觉修改；不能把新游戏首轮一句“给我测试包”解释成所有美工免检，也不能把单个页面授权扩大到其他页面或功能。

授权可以分散在连续消息中：前面已经要求修某处美工，修复完成后再说“给我测试包”，应结合当前返工上下文识别，不要求用户重说完整句子。保留相关原话及其范围，不能只因最后一句短就退回首轮验收。

如果同一批请求还涉及奖励、存档、输入或关卡逻辑，视觉部分仍按上述授权处理，实际变化的功能节点按依赖计划验证；不重新验无关功能。仅改图片字节或显示文案时，不为声音、玩法、关卡另开测试。

## 2. 用单独的授权记录，不改写测试历史

以下记录由 AI 从当前用户原话、实际交付文件和本次改动自动整理，不让用户填写 JSON、寻找哈希或再次确认。它用于防止拿错版本，不能变成新的审批节点。

完成指定修改、准备当前 Web 和已处理 Native 后，通过 `returned_art_acceptance.py record` 记录授权：

```sh
python3 <skills>/remake-core/scripts/returned_art_acceptance.py --project PROJECT record \
  --previous-zip PREVIOUS_DELIVERED_ZIP \
  --instruction-file EXACT_USER_REQUEST.txt --scope-file REQUESTED_VISUAL_SCOPE.json \
  --web CURRENT_WEB --native CURRENT_NATIVE
```

输入使用本次真实用户原话和实际修改范围；AI 先将真实改动逐项归属本次请求，不能用单页授权覆盖未经说明的其他页面变化。范围文件是数组，每项含工程相对 `path`、`kind`（`image/crop/font/text/layout`）和实际修改要求 `request`，例如 `[{"path":"assets/ui/checkin.png","kind":"image","request":"去掉签到文字重影，按用户要求改完交测试包"}]`；该示例不能原样替代真实文件和原话。若旧包已不在本机，可按工具支持的 `--previous-delivery` 读取已有交付记录，不能伪造上一轮交付。记录保存于 `.tiktok-kit/returned-art-acceptance.json`，标记 `user_accepted`、`ai_art_rechecked:false`，绑定上轮交付身份与当前源码、Web、Native 的真实指纹。更换这些输入后，旧授权不能冒充新版本；先确认新增变化仍属于原请求，再为实际候选记录对应授权，不重新跑美工。

若工程已使用 `workflow.json`，AI 同步建立本轮 `returned` 执行分支：本次授权的视觉节点保留原节点与历史结果，标明在本轮免复验；本轮交付节点的 `after` 只列实际仍需的技术证据，不继续把已获授权免验的旧美术节点列为必须重新通过的前置条件。授权身份由 writer/preview 的独立记录核对，不把授权记录送进 `check_workflow.py` 冒充 `passed:true`。这只改变本轮被授权视觉项的调度；功能依赖不能随之移除，也不删除或改写旧 ledger。

返工授权记录只说明用户接受的变更范围与实际候选身份。原分项技术证据保留其原始结论。

writer 的 `layout_state` 原来混合视觉采集与隐藏启动测量。本次授权下，视觉页面项记为 `user_accepted`、`passed:null`，不拍图、不扫描布局；启动下载量和启动声音由独立 `@startup` 节点处理，有效同输入记录沿用。其他功能节点不因视觉接受而免验；旧判定器无法确认兼容时先定位记录范围，不自动启动整套浏览器。

本次授权下，不再启动改图后的 `art_check.py`、全页面看图、两视口采集、中文 OCR、逐图审美或以“重新生成回执”为名的重复美工检查。制作时仍需正确完成裁切、绑定、导出与引用更新；这些是交付修改本身，不额外扩成验收轮次。

## 3. 出包障碍必须落实到下一步动作

用户目标是拿到同版测试包与试玩入口。遇到脚本拒绝，继续读取具体原因并处理对应节点：

| 拦在哪里 | 继续做什么 | 不应做什么 |
|---|---|---|
| 旧视觉证据 | 仅受影响的真实视觉问题按本次任务处理 | 补写完整美术凭据 |
| 新旧源码、Web、Native 不一致 | 找到本轮实际构建，同步或只补缺失导出 | 把同步问题变成全游戏检查 |
| 预览服务未启动或快照过期 | 恢复当前版本的本地服务，读回入口与版本 | 用旧版链接凑交付；停在“链接未放行” |
| 当前 ZIP 体积、分包、入口错误 | 修包结构、打包配置或本次真实资源问题，再核最终文件 | 用视觉授权放行损坏包；顺便重跑玩法和美术 |
| 改动引入实际运行缺陷 | 定位对应依赖，修复并只验证该节点 | 以“保险”为由重跑原来的整套流程 |

不要用“门禁不让出包”作为完成答复。能在现有授权内修复就继续；真正缺外部工具、原件或权限时，报告具体缺项、已完成文件、当前节点及恢复后的下一步，不能伪称交付完成。最终 ZIP 的本次体积/分包检查、平台已拒绝同字节包的处理、同版可用试玩入口仍按用户的交付要求执行；这些不能触发额外美工审查。

## 4. 人工快查放在原有 Native 试玩与反馈节点

人在熟悉游戏的情况下通常更快判断喜好、文字是否自然、是否符合自己给出的参考；这类收益要通过实际用时记录确认，不预设固定节省比例。将下表适用项随同版 Native 试玩交给用户，复用原来的试玩时间，不新增一轮等待或独立审批。

下表“AI 负责”用于首次制作或实际变化的技术引用，不给已授权返工重新加检查：本次视觉免复验仍跳过几何、裁切、看图等美工复验；只有实际功能改动才验证相应技术节点。

| 人工优先看 | 给用户的具体提示 | AI 负责的不同问题 |
|---|---|---|
| 画风和风格选择 | “首页这组新按钮是否符合原来的样子？” | 素材身份、实际显示尺寸、图层绑定；不反复做相同主观评比 |
| 固定文案与图意 | “签到页这两句英文和图标表达的是不是你要的意思？” | 实际字符、数字/斜杠成组制作、长文预算及指定改动是否落盘 |
| 肉眼明显的排版和残留 | “只看这次改过的签到页：旧字是否还叠着、文字是否压按钮？” | 有改动的自动几何/裁切判据；同一项已有合格证据不再执行 |
| 个人审美与玩法体验反馈 | “这次修改的颜色、字号或手感是否需要再调整？” | 用户看不到的延迟回调、重复发奖、保存读回、冷启动分支；仅本次受影响或缺有效覆盖的节点 |

先为每项标明主要判定者：适合人工且尚未判断的视觉选择交给用户，AI 不再做同项审美巡检；已有 AI 或人工有效结论的项不再列成必做复查。自动测量与主观选择确实判定不同问题时才各保留一项，不能换名称重复同一个判定。

每次正文列 **3–5 条以内**、只包含这款游戏实际存在且本轮需要用户判断的项目。只改一处就一条；按同一页面到达路线排列，不要求用户从头玩所有关卡，不让用户查日志、图集坐标或反复冷启动。用户回复一个问题即可进入对应节点，不要求先填完整表。

首次正式 Native 试玩仍先完成技术正确性所需的制作与首次证据；主观风格选择放在此次用户试玩，不在 AI 后续阶段重复审美。已交付返工且用户要求“改完出包”时，上述清单只作为交包后的可选快看提示：**不等用户做完、不因未回答阻止出包、不把未回答写成人工实测通过。** 这次视觉交付状态来自第 1 节的授权；人实际看过后的结论另记。

人工快查不能替代用户不容易发现的运行问题，也不能把首件几何检查误当作全游戏真实运行覆盖。若用户指出了新的视觉问题，按新的指定范围修，不附加一套“人工检查后再由 AI 全部复核”的流程。

## 5. 生成阶段减少出错与返工

本轮沿用 [少返工的制作与采集](../../remake-art/references/art-iteration-workflow.md) 和 [制作预防](../../remake-art/references/production-prevention.md) 的已有工具，不另建一套全量检查。先按实际资源组成分路：

| 工程的主要情况 | 第一批制作时做什么 | 可以省下什么 |
|---|---|---|
| 图集、Spine 或带字贴图较多 | 从原 atlas/meta 的真实区域和旋转、trim、offset 还原切片；先核一个容易越界的代表，保留原坐标关系。骨骼附件使用者与序列帧分别列出，不能只凭整图外观切 | 猜坐标、逐图人工找边、错切后整图重生、批量接入后才发现邻格污染 |
| Label 较多、带字贴图较少 | 一次定稿实际英文、最长数字及符号；用现有排版预算找最窄槽和共享字体消费者。相同配方与同输入沿用；固定按钮、长说明、数值栏分别处理 | 文案未定就生图；同一句重生多次；每接一个 Label 都重新构建 |
| 图片与运行文字混用 | 先列谁负责每一行字和图标，清楚标记保留层、替换层、动态层；固定整图按钮不得再叠旧字，数字/单位/符号用同套字形与独立显示槽 | 签到重影、帽子红边、重复视频图标、符号按 PNG 像素放大 |

按共享配方、槽位、字体、裁切和渲染机制选择代表首件；布局或裁切机制不同就分组，不能用首页一个样品代表所有图集与弹窗。已经有有效同输入首件证据的沿用。对低风险的同模板替换不重复展开整套美术手册；确实存在 Spine、旋转切片、动画尺寸回写时才读对应专门规则。

将文字定稿、槽位预算和完整图层替换方案一次给到生成任务。源图完整、接入有错时改接入；原图已经切断或含邻格时改切图配方。共因修正合批，候选稳定后 Web/Native 各补需要的一次导出；不是每张图单独构建，不为截图身份误差重新生图。

## 6. 节点汇报与耗时依据

返工节点使用 `returned/问题ID/制作`、`returned/问题ID/功能复验`、`delivery/同版试玩`、`delivery/最终ZIP` 等实际需要的稳定名称。每步报告正在解决什么、本次执行/沿用/用户授权免复验、实耗、结果和下一步。视觉授权项写“按你的返工交付要求接受，未重跑 AI 美工检查”；不能只写“通过”。

计时分为制作、必要构建、受影响检查、人工试玩等待、最终交付文件核对。比较时同时报告改图次数、构建次数、浏览器启动与采集次数；未做真实同条件对照，不宣称已省多少分钟。授权免复验记录与技术通过记录分别统计，避免把少验的项目说成检测变快或零漏报。
