# 唯一写包入口与原检查记录消费

适用于英化首次制作、接收成品、交付后局部返工和同包重发。两种输入路线保留，写包收敛到同一个后端。当前任务授权与局部范围优先。

## 唯一入口

正式命令固定使用 `remake-core/scripts/make_tiktok_zip.py`，唯一后端是 `make_tiktok_zip.write_package`。`build_checked_zip.py` 的旧 CLI 和 `build()` 只映射参数到这个后端；`--app-id` 与旧 `--expected-app-id` 同义。失败后回到报错节点，不换旧 writer、手工压缩或另选一套检查解除拒绝。

原两个实现的实质要求保留：源码准备、AD6、原音频约束、Native 资源路径、WebP 解码、实际存档与持久化覆盖、项目扩展、interaction/audio 和最终 ZIP 字节。不存在“严格入口”和“轻量入口”供 AI 选择。

## 固定生产顺序

1. 开工辨认中文源码首次制作，或已有源码/测试包的接收与局部维护。按现有计时工具报告阶段、当前节点和实际用时；旧证据导入保持原执行时间，未提供的历史记录不伪装为通过。
2. 先完成本次适用的功能/六类广告设计与接线计划，再集中制作相应页面、图片、文字和声音。新增界面先走美工 Skill，原游戏画风与局部范围不变。
3. 同一批已确认改动收齐后，按实际引擎准备、导出并完成 `tiktok_finalize`，固定 Native 字节。之后执行各自节点真正缺失或受影响的检查，每项保存原结果、依赖、条件和原始证据。已有有效项直接沿用。不要先验收，再在 writer 里改 adapter、平台件或 PNG。
4. 需要的存档探针、持久化覆盖和项目 QA 扩展在其生产/检测节点形成证据。`writer_proofs.py prepare` 按种类只执行新/变动项；无变化的结果沿用，同输入失败先修原因。机器给出缺项后继续该节点，不从头准备整个游戏。
5. 用户试玩反馈只返回相应节点；修正后只补验真实影响项。已有记录、页面与浏览器空间按原规则复用，不因更换 AI、构建标签或交接阶段加测。
6. 写包只消费准备结果和有效记录：先只读核计划与依赖，再调用唯一 writer。最后 `prepare_delivery.py` 一次核对本次实际 ZIP、分包/体积/CRC、官方 CLI 和同版试玩，按现有 H5 交接。这里没有第二次玩法或美术验收。

以上是依赖顺序，不改变英化原有五阶段计时。独立制作任务可以按已有计划并行，但固定候选、检查、写包和交付之间按此依赖衔接。

## 执行者无关的状态路由

| 机器状态 | 确定动作 | 后续节点 |
|---|---|---|
| 输入、规则、条件与原证据均有效 | 引用原 key、原记录及时间；不执行检查 | 下一个节点 |
| 真实改动只影响一个或几个检查 | 只核这些检查的执行计划 | 对应生产/检测节点 |
| 该输入已有失败 | 修输入或定位实际环境故障，保留原失败 | 修复节点；不重复失败命令 |
| 原件丢失但冻结副本有效 | 从冻结证据读取或恢复原件 | 原节点续跑，不重测 |
| 证据无法恢复或与输入不符 | 仅修复该条证据，确需时只补验该独立项 | 该证据的生产节点 |
| 改动没有明确依赖归属 | 查实际调用、资源使用者和旧证据，补依赖映射 | 范围修复；不全量兜底 |
| Native 尚未准备或写包中会变字节 | 回 Native 准备；再只补实际受影响项 | 原 writer |
| 最终 ZIP/CLI/同版试玩核对失败 | 修复具体文件或入口问题 | 最终交付核对 |

`repair_required`、`scope_required`、`plan_ready` 都是继续执行的状态，不是交付完成。能在当前授权中解决的缺口由当前 AI 处理，不以“尚未生成 ZIP”收尾。

## 生产证据与旧总表

```sh
# 在对应生产节点形成一次；后续同输入会引用原结果。
python3 <skills>/remake-core/scripts/writer_proofs.py prepare \
  --project <工程> --native <Native> --web <Web> --kind reward-storage
python3 <skills>/remake-core/scripts/writer_proofs.py prepare \
  --project <工程> --native <Native> --web <Web> \
  --coverage <持久化覆盖.json> --kind runtime-coverage
```

受检项目需要 registered project QA 时，使用同一 producer 的 `--kind project-qa` 和真实项目输入。writer 对这些结果只读消费，缺一项就明确回到这一项；不会自己调用存档 VM、项目 adapter 或浏览器补证。

旧历史问题清单按当前 catalog 动态生成，行数不是协议。`known_issue_checkpoints.py` 将已有、实际验证过的行、入口盘点、独立奖励交叉状态与各奖励状态分成稳定的 `known.*` 节点，使用现有 ledger 保存证据。后续只重核失效项的证据，其余沿用；不把普通版本号变化当作新观察。依赖范围写进原 `check-inputs.json`，不能用无关兜底选择器吞掉真实变化。

一次批次里 A 失败、B 通过时，只要全局身份与结构有效，就分别冻结 A 的失败和 B 的通过；修好 A 后只核 A，B 保留原证据和时间。结构、库存身份或未知归属错误必须明确解决，不能猜成单项失败，也不能把整批尚未完成写成全部通过。

`--review` 接收已有清单，未提供时不要求为了写包另填整张表。`not_recorded`、`project_supplement` 或尚未映射的义务不是通过，更不能写成完整验收。首次制作的实际义务仍在各自生产节点完成；用户已授权的旧游戏局部维护不追补未改动部分的历史总表。实际失败、过期证据和已登记未修复问题仍须处理。

AI 名称和 `test_executor` 只记录来源，不产生“GPT 重跑全部自动检查并再走三条流程”的要求。已有附加审阅若存在真实不一致，定位到具体 ID 修复；不扩大到整类重测。原游戏观察时间未知就写未知，证据注册/核对时间不能冒充新的游戏实测时间。

BUILD-03 的统一 writer 拒绝契约在 Skill 更新时由工具级测试覆盖一次。游戏项目不再为填写该行额外反复生成检查 ZIP；自写的绕行打包器不是正式入口。

## 保留的精确边界

同次 writer 的 Native 预检和 ZIP 回读，以及同次 `prepare_delivery` 内的文件层核对，可能需要同一底层 host/触控 VM。`audit_invocation()` 仅在这次调用内对精确相同字节、工具与环境去重；不同输入、失败、未知依赖和下一次交付不会沿用该短缓存。最终 ZIP 的 CRC、配置和体积仍读取实际文件。

旧 STORAGE-01 与启动回执通过[精确依赖迁移](scoped-storage-startup.md)保留原基线和原观察，消费核对当前实际读取集，不改旧哈希。已证明无关的资源变化沿用原记录；未知依赖先修映射，只补真实受影响的独立项，不自动重开功能矩阵。

## 资源生产与经验维护

首次完整制作的[资源分包前置](resource-package-prepare.md)发生在资源整理及构建准备阶段，Native 后校准真实字节；writer 不据此增加另一轮资源重排或运行器。成功交付后由入口轻量收集[已有经验](production-learning.md)，维护候选是否冲突、缺材料或队列繁忙均不改变当前游戏已满足的交付条件。共享修复优先回到模板、资源组织和接入节点，按正式版本统一发布，不由各游戏对话直接覆盖安装文件。
